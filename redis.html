Redis optionnel

Redis est maintenant active par defaut pour les OTP SMS et e-mail (OTP_CACHE_STORE=otp, base 3). Le cache general, les sessions configurees et les compteurs de connexion utilisent toujours PostgreSQL. Les comptes et les tokens Sanctum restent dans PostgreSQL. Redis doit etre demarre avant les inscriptions, les verifications OTP et la diffusion en temps reel Reverb (file broadcasts en base 4).

Le client PHP predis/predis est fourni par Composer : aucune extension PHP Redis n'est necessaire, y compris sur Windows. Le serveur deja fourni par Laragon est utilise en local, sans Docker. Horizon reste absent.

Revenir explicitement a un fonctionnement sans Redis

OTP_CACHE_STORE=database
CACHE_STORE=database
CACHE_LIMITER=database
SESSION_DRIVER=database
QUEUE_CONNECTION=database
BROADCAST_QUEUE_CONNECTION=database

Activer Redis pour les compteurs de connexion seulement

Une fois un serveur Redis accessible :

REDIS_CLIENT=predis
REDIS_HOST=127.0.0.1
REDIS_PORT=6379
REDIS_USERNAME=null
REDIS_PASSWORD=null
REDIS_CACHE_DB=1
CACHE_LIMITER=redis

Le cache general et les sessions peuvent rester dans PostgreSQL. Les memes regles de limitation s'appliquent dans les deux modes.

Activer aussi le cache et le stockage des sessions

CACHE_STORE=redis
CACHE_LIMITER=redis
SESSION_DRIVER=redis
REDIS_SESSION_DB=2

Quand SESSION_DRIVER=redis, la connexion nommee sessions est selectionnee automatiquement. Les sessions utilisent une base Redis distincte du cache (2 contre 1), afin qu'un vidage du cache ne supprime pas les sessions. SESSION_CONNECTION peut remplacer ce choix explicitement.

Si l'hebergeur fournit des URL, utiliser REDIS_URL pour le cache/les queues et REDIS_SESSION_URL pour les sessions, avec la base correcte dans chaque URL. Une base specifiee dans l'URL peut remplacer REDIS_CACHE_DB ou REDIS_SESSION_DB. En production, utiliser les identifiants et les exigences TLS du fournisseur.

Le changement de stockage de session ne transfere pas les sessions existantes : une reconnexion peut etre necessaire. Changer SESSION_DRIVER ne met pas en place l'authentification SPA par cookies : les routes actuelles de connexion emettent toujours des tokens Sanctum. Ce mode web devra etre configure separement avec CSRF et les domaines autorises.

Apres toute modification du .env :

php artisan config:clear

En production, reconstruire ensuite le cache de configuration et redemarrer les processus persistants concernes. Pour verifier Redis, ouvrir php artisan tinker, puis executer :

Illuminate\Support\Facades\Redis::connection('cache')->ping();
Illuminate\Support\Facades\Redis::connection('sessions')->ping();

Redis est optionnel par choix de configuration, sans basculement automatique en cas de panne. Si Redis est selectionne puis devient indisponible, les requetes API touchees par une erreur de connexion Predis retournent 503. Les compteurs ne sont pas recrees silencieusement dans PostgreSQL. Pour revenir a PostgreSQL, reconfigurer explicitement les stockages puis vider le cache de configuration ; les sessions/compteurs Redis ne sont pas transferes.

Limitation de connexion

POST /api/mboka-services/v1/auth/login utilise le limiteur Laravel login :

  • 3 echecs dans une fenetre de 15 minutes pour un meme compte et une meme IP, partages entre telephone et e-mail ;
  • 30 requetes par minute pour une meme IP, tous numeros confondus.

Ces seuils sont configurables via LOGIN_MAX_ATTEMPTS=3, LOGIN_DECAY_MINUTES=15 et LOGIN_IP_RATE_LIMIT_PER_MINUTE=30. La limite compte + IP compte les echecs HTTP 422 (identifiants invalides et erreurs de validation). Les connexions reussies ne consomment pas les essais et ne remettent pas les echecs precedents a zero. La fenetre de 15 minutes commence au premier echec ; apres 3 echecs, les requetes suivantes sont bloquees jusqu a son expiration. La limite globale par IP compte toutes les requetes. Le meme endpoint protege le mobile et le web, quel que soit le User-Agent. Le format local avec country_id et son equivalent international partagent la meme limite. Les cles des compteurs ne contiennent pas le numero en clair.

Une limite depassee retourne HTTP 429, success=false, un message localise (fr/en/ln), retry_after en secondes et l'en-tete Retry-After. La limite expire automatiquement apres sa fenetre.

Derriere un reverse proxy en production, configurer uniquement les proxies de confiance pour que l'IP utilisee soit celle du client. Ne pas faire confiance aux en-tetes IP provenant directement d'Internet.

Tests

La suite standard ne necessite pas Redis. Elle utilise une base PostgreSQL de test dediee et un cache en memoire pour l'isolation, avec un test specifique des compteurs PostgreSQL et un test de panne Redis simulee. La selection du client Predis et la separation cache/sessions sont egalement verifiees sans serveur Redis.

php vendor/phpunit/phpunit/phpunit --do-not-cache-result

Horizon reste une evolution ulterieure. Les queues generales conservent leur stockage PostgreSQL par defaut ; seule la file de diffusion Reverb utilise Redis via la connexion redis-broadcasts.

Stockage OTP optionnel

OTP_CACHE_STORE=otp conserve maintenant l empreinte du code, les echeances et les compteurs dans Redis. Cette valeur est preparee dans .env.example et utilisee par defaut dans config/otp.php :

OTP_CACHE_STORE=otp
REDIS_OTP_DB=3
# REDIS_OTP_URL=redis://127.0.0.1:6379/3

Le store otp utilise une connexion Redis dediee, distincte du cache et des sessions. Ne pas reutiliser leurs bases si un vidage du cache ne doit pas invalider les codes. Aucun basculement automatique en cas de panne. Les routes de verification et de renvoi utilisent les memes regles, sur mobile comme sur web.

Les operations OTP sont serialisees par verrou de ligne PostgreSQL sur le compte : les compteurs ne peuvent pas etre remis a zero par deux renvois concurrents, et une validation ne peut pas creer deux tokens pour le meme code. Le compte, son etat de verification et les tokens Sanctum restent dans PostgreSQL.

Les OTP d inscription SMS et e-mail utilisent le meme store et les memes limites. Le canal et le destinataire sont lies au code ; valider un e-mail ne confirme pas le telephone. Redis ne transporte aucun message : les SMS passent par Infobip, les e-mails par SMTP (Mailtrap Sandbox en developpement).

Demarrer Redis localement avec Laragon

Le script utilise le serveur Redis deja installe dans C:\laragon\bin\redis\redis-x64-5.0.14.1 et cree sa configuration et ses donnees dans .local/redis (ignore par Git). Aucun Docker ni service Windows supplementaire n est necessaire.

powershell -NoProfile -ExecutionPolicy Bypass -File scripts/redis.ps1 start
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/redis.ps1 status
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/redis.ps1 stop

Demarrer Redis apres chaque redemarrage du PC, avant de lancer les parcours OTP. Le processus est lance en arriere-plan sans fenetre. Il ecoute uniquement sur 127.0.0.1:6379, limite sa memoire a 64 Mo et utilise noeviction pour ne pas supprimer des compteurs encore valides quand la memoire est pleine. La persistance AOF est activee. Le parametre -RedisDirectory permet de designer un autre dossier Redis Laragon ; -Port permet de changer le port (adapter aussi REDIS_PORT dans .env). Le script refuse d arreter une instance qu il ne gere pas. Un serveur deja present sur ce port est reutilise ; ses propres parametres de securite, memoire et persistance doivent alors etre geres par son proprietaire.

La version Redis embarquee dans cet ancien Laragon sert uniquement au developpement local. En production, utiliser un serveur Redis maintenu, avec authentification, reseau prive et TLS selon l hebergeur, et les variables REDIS_* correspondantes.

Le code expire au bout de 5 minutes, mais l entree Redis peut durer plus longtemps (par exemple environ 16 minutes) pour conserver les quotas d envoi et les blocages. Une validation reussie supprime immediatement l entree ; sinon Redis la supprime automatiquement au terme du TTL. Un redemarrage non propre peut perdre les dernieres ecritures AOF non synchronisees. Les codes et compteurs du stockage PostgreSQL precedent ne sont pas transferes : les comptes en attente doivent demander un nouveau code sur /auth/otp/resend.

Les OTP de recuperation du compte et de changement de contact utilisent egalement le store OTP dedie. Ils disposent de cles separees par compte et par usage et ne peuvent pas servir a valider une inscription. Les compteurs restent presents jusqu a leur TTL apres succes, mais les empreintes et correspondances des codes utilisables sont invalidees. Les mots de passe proposes ne sont jamais stockes dans Redis. Le mot de passe final hache et les tokens restent en PostgreSQL. Les verrous de ligne utilisateur serialisent connexion, modification des contacts et changements de mot de passe.

File Reverb sur Redis

BROADCAST_CONNECTION=reverb reste le transport WebSocket. BROADCAST_QUEUE_CONNECTION=redis-broadcasts selectionne la file Redis dediee (connexion Redis broadcasts, REDIS_BROADCAST_DB=4, REDIS_BROADCAST_URL facultatif). Cette base est distincte du cache (1), des sessions (2) et des OTP (3). Ne pas utiliser un vidage global FLUSHALL pour vider le cache.

Lancer Redis puis php artisan reverb:start et php artisan queue:work redis-broadcasts --queue=broadcasts --tries=5 --timeout=30. Les transactions annulees ne diffusent pas d evenements ; les echecs de diffusion sont reessayes puis conserves dans failed_jobs PostgreSQL. Si Redis est indisponible avant l ajout du job, le message reste enregistre, l erreur est journalisee et le rattrapage HTTP retrouve le message : aucun basculement automatique ni re-envoi automatique de cet evenement non mis en file.

Pour un retour explicite a la file PostgreSQL, definir BROADCAST_QUEUE_CONNECTION=database, vider le cache de configuration et lancer le worker database --queue=broadcasts. Drainer aussi l ancienne file avec son worker pour ne pas abandonner les evenements en attente ; changer la configuration ne transfere pas les jobs. REVERB_SCALING_ENABLED reste false sur une instance.

Notifications Expo

La file redis-push/queue push utilise REDIS_PUSH_DB=5, distincte des OTP et de Reverb. EXPO_PUSH_ENABLED active les envois, EXPO_ACCESS_TOKEN configure le secret serveur optionnel Expo et REDIS_PUSH_URL permet une connexion de production dédiée. Les notifications et l’outbox restent en PostgreSQL pour permettre une reprise après panne Redis. Lancer php artisan queue:work redis-push --queue=push --tries=1 --timeout=30 et le planificateur Laravel pour push:maintain chaque minute. Voir le guide API pour les installations, les reçus, les prérequis Expo et les limites de livraison.

Alertes e-mail et Web Push différées

La connexion redis-web-notifications utilise REDIS_WEB_NOTIFICATIONS_DB=6 et la queue web-notifications. Elle conserve une outbox PostgreSQL et réessaie après panne Redis. Lancer son worker et le planificateur notifications:maintain-web ; le guide API détaille le délai de dix minutes, la présence des onglets, la priorité à l’e-mail vérifié, les clés VAPID et le lancement OpenSSL sous Windows.
