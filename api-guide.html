Utiliser l API Mboka Services

L API connecte clients et prestataires locaux. Son prefixe est /api/mboka-services/v1.

Faire une premiere requete

Demarrer PostgreSQL, Redis pour les OTP, puis Laravel depuis le dossier du projet :

powershell -NoProfile -ExecutionPolicy Bypass -File scripts/postgres.ps1 start
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/redis.ps1 start
php artisan serve

Consulter le catalogue public :

GET http://127.0.0.1:8000/api/mboka-services/v1/categories
Accept: application/json
X-Locale: fr

Les langues disponibles sont fr, en et ln. Le fichier openapi.json est importable directement dans Postman : Import > fichier ou URL du fichier OpenAPI de la documentation.

Authentification mobile et web

L implementation actuelle utilise des tokens Bearer Sanctum, sur mobile comme sur le web. POST /auth/register cree un compte en attente et retourne HTTP 202 avec data.verification_id, expires_in et resend_after, sans token. POST /auth/otp/verify confirme le contact choisi (SMS ou e-mail) et retourne un token dans data.token. Les connexions suivantes par POST /auth/login utilisent telephone ou e-mail verifie + mot de passe et retournent un token si le contact choisi est deja verifie. Pour les routes protegees :

Authorization: Bearer VOTRE_TOKEN
Accept: application/json

Le mot de passe d un compte est hache dans PostgreSQL. L empreinte du token est conservee dans personal_access_tokens. POST /auth/logout revoque le token courant. Redis ne remplace pas ce stockage.

GET /auth/me retourne le compte connecte. Les comptes client et provider peuvent s inscrire ; les droits administrateur ne sont pas accessibles par inscription publique.

Valider l inscription par OTP SMS ou e-mail

  1. Appeler POST /auth/register avec les champs habituels du compte et verification_channel=sms ou email. Par defaut : sms. Le telephone et le pays restent requis ; l e-mail est obligatoire pour le canal email.
  2. Conserver data.verification_id de la reponse HTTP 202.
  3. Recevoir le code sur le canal choisi (dans Mailtrap pour les tests e-mail), puis envoyer les donnees suivantes :
POST /api/mboka-services/v1/auth/otp/verify
Content-Type: application/json

{
  "verification_id": "UUID_RECU_A_L_INSCRIPTION",
  "code": "123456"
}

Le code doit etre une chaine de 6 chiffres. Il expire apres 5 minutes. Apres 3 codes incorrects, verification et renvoi sont bloques pendant 15 minutes. Le code est consomme une seule fois ; le succes renseigne phone_verified_at pour sms ou email_verified_at pour email, sans confirmer l autre contact, et retourne un token Sanctum. Les anciens tokens du compte sont revoques.

Pour renvoyer, appeler POST /auth/otp/resend avec verification_id, apres 60 secondes. Maximum 3 envois par compte sur 15 minutes et 10 demandes par IP sur 15 minutes, inscription et renvoi cumules. Le renvoi invalide l ancien code, sans remettre les echecs a zero. Un echec Infobip ou SMTP consomme aussi un essai d envoi pour eviter les boucles de facturation.

Les comptes deja presents restent non verifies apres migration. Avec le bon mot de passe, POST /auth/login retourne HTTP 403, error_code=phone_verification_required (ou email_verification_required pour les nouvelles inscriptions par e-mail), data.channel et data.verification_id pour reprendre le parcours. Aucun token n est delivre avant verification. Les anciens tokens ne donnent pas acces aux routes metier protegees tant que le contact choisi n est pas verifie ; logout reste possible.

Si l envoi echoue, HTTP 503 retourne verification_id lorsque le compte a ete cree. Le compte n est pas supprime : reprendre avec resend apres le delai indique. Un code perdu ou expire exige un renvoi.

Limites de connexion

POST /auth/login autorise 3 echecs par compte + IP (telephone et e-mail partages) sur une fenetre de 15 minutes qui commence au premier echec. Les connexions reussies ne consomment pas ces essais. La quatrieme tentative est refusee jusqu a expiration de la fenetre, meme avec un mot de passe correct. Il existe aussi une limite de 30 requetes/minute par IP, tous numeros confondus.

En cas de blocage : HTTP 429 avec success=false, message, retry_after et en-tete Retry-After. Attendre ce delai avant de reessayer. Les memes compteurs sont utilises par le mobile et le web. PostgreSQL est le stockage par defaut ; Redis est activable par configuration.

Comprendre les modules

Module Usage
countries Pays et villes de reference
categories Groupes de metiers ; administration reservee aux admins
services Catalogue des metiers ; approbation admin des propositions prestataires
provider-services Offres des prestataires, prix et disponibilite
locations Carnet d adresses prive et choix de l adresse par defaut

medias Images et videos de profil, portfolio et pieces jointes

Service, ProviderService et ServiceRequest representent respectivement un metier, une offre commerciale et une intervention demandee.

Parcours d une intervention

  1. Le client cree son compte et sa localisation.
  2. Il choisit un service approuve et cree une demande.
  3. Il peut choisir un prestataire immediatement ou l affecter plus tard.
  4. Le prestataire discute puis propose un prix et un rendez-vous ; le client confirme ou refuse.
  5. Le travail demarre, le prestataire declare la fin puis le client la confirme ou signale un probleme.

Statuts du parcours actuel : pending -> proposed -> accepted -> in_progress -> awaiting_confirmation -> completed. Le client confirme la proposition puis la fin ; un probleme donne disputed. Le refus donne rejected, l annulation cancelled. Voir le parcours detaille ci-dessous.

Fichiers et erreurs

Pour les medias, utiliser multipart/form-data avec file, mediable_type, mediable_id et media_type. Une photo de profil doit etre une image. Les images de profil et anciens portfolios utilisent le disque public. Les fichiers des publications et des interventions utilisent des disques prives et des routes de consultation controlees. Les limites dependent de leur usage et des limites PHP/serveur.

Les erreurs 401 indiquent une authentification manquante ou invalide ; 403 une action interdite ; 422 une validation ou regle metier non respectee ; 429 un depassement des limites. Si Redis est configure puis inaccessible, une erreur de connexion Predis est rendue en 503.

Ce qui reste a construire

La documentation publiee ne deploie pas le backend. Les sessions SPA par cookies, les paiements, Horizon et la recherche geographique par distance ne sont pas encore exposes comme fonctionnalites completes. PostGIS est installe et teste ; cela ne signifie pas qu une route de recherche par rayon existe deja.

Configurer Infobip et tester sans SMS reel

Par defaut, SMS_DRIVER=fake ne contacte aucun prestataire. En local, le dernier SMS de chaque verification est ecrit dans .local/sms-outbox/<verification_id>.json. Lire ce fichier prive pour recuperer le code, puis tester verify dans Postman. Ce dossier est ignore par Git. Les tests automatises capturent les messages en memoire. Le mode fake est refuse en production.

Pour activer de vrais SMS, renseigner uniquement dans le .env prive :

SMS_DRIVER=infobip
INFOBIP_BASE_URL=https://VOTRE_COMPTE.api.infobip.com
INFOBIP_API_KEY=VOTRE_CLE_PRIVEE
INFOBIP_SENDER=VOTRE_EXPEDITEUR_AUTORISE

Puis executer php artisan config:clear. Le compte Infobip doit autoriser les SMS et l expediteur choisi. La cle reste cote Laravel. L API utilise /sms/3/messages avec Authorization: App, et distingue un message accepte d une livraison effectivement recue. Un compte d essai peut limiter les destinataires aux numeros verifies chez Infobip.

Les codes ne sont jamais retournes dans les reponses API ni ecrits dans les journaux applicatifs. Seul le mode simule local possede une boite SMS privee contenant le texte du message. Ne pas utiliser cette simulation en production.

Les tests automatises utilisent des reponses HTTP simulees et n envoient aucun SMS.

OTP e-mail avec Mailtrap Sandbox

Mailtrap Sandbox capture les courriels de developpement : ils apparaissent dans son interface, pas dans la boite mail reelle du destinataire. Creer un sandbox dans Mailtrap, ouvrir son onglet Integration, selectionner SMTP/Laravel et copier les identifiants uniquement dans le fichier .env prive :

MAIL_MAILER=smtp
OTP_MAILER=smtp
MAIL_SCHEME=smtp
MAIL_HOST=sandbox.smtp.mailtrap.io
MAIL_PORT=2525
MAIL_USERNAME=IDENTIFIANT_DU_SANDBOX
MAIL_PASSWORD=MOT_DE_PASSE_DU_SANDBOX
MAIL_FROM_ADDRESS=noreply@mboka.test
MAIL_FROM_NAME="Mboka Services"
MAIL_TIMEOUT=10

Executer ensuite php artisan config:clear. MAIL_SCHEME=smtp autorise la negociation STARTTLS du transport Symfony ; la verification des certificats reste active. Sur ce poste Windows, si PHP ne trouve pas les certificats racines, configurer curl.cainfo et openssl.cafile dans le php.ini avec le fichier de certificats Laragon.

Exemple Postman, POST /api/mboka-services/v1/auth/register (remplacer country_id par celui retourne par GET /countries et utiliser un nouveau numero) :

{
  "name": "Client Mailtrap",
  "country_id": 7,
  "phone": "0999000123",
  "email": "client@example.test",
  "verification_channel": "email",
  "password": "password",
  "password_confirmation": "password",
  "account_type": "client"
}

La reponse 202 contient data.channel=email, verification_id, expires_in et resend_after. Copier le code a six chiffres affiche dans Mailtrap et appeler /auth/otp/verify avec verification_id et code (chaine). Le token recu permet /auth/me et les routes metier. email_verified_at est renseigne, phone_verified_at reste null. La connexion suivante accepte telephone ou e-mail verifie, avec le mot de passe.

/auth/otp/resend utilise le canal enregistre lors de l inscription : aucun changement de canal ni de destinataire n est autorise par cette route. Les comptes existants gardent sms ; cette evolution ne confirme pas leurs contacts automatiquement. Les comptes ayant deja un numero doivent reprendre leur verification existante.

Les limites et le stockage OTP optionnel Redis sont communs aux deux canaux : 5 minutes, 3 erreurs puis 15 minutes de blocage, renvoi apres 60 secondes, 3 envois/15 minutes par compte. L envoi est synchrone et ne necessite aucun worker. Une panne SMTP retourne 503 et conserve le compte en attente avec verification_id ; apres correction, reprendre avec resend sans recreer le compte. Les transports log/array/failover sont refuses pour les OTP e-mail afin de ne pas journaliser les codes ni annoncer un envoi fictif. Le message existe en HTML et texte, localise via X-Locale.

En production, remplacer les identifiants du Sandbox par ceux d un service d envoi reel, avec un expediteur et un domaine autorises. Le Sandbox n est pas un service de livraison vers les utilisateurs.

References : integration SMTP Mailtrap, Email Sandbox.

Le stockage OTP est maintenant Redis par defaut (OTP_CACHE_STORE=otp, base 3), pour les SMS comme pour les e-mails. Les comptes, les validations et les tokens Sanctum restent en PostgreSQL. Redis indisponible implique un refus temporaire HTTP 503, sans basculement silencieux. Les anciens codes PostgreSQL ne sont pas transferes ; demander un nouveau code apres le changement de stockage. Voir le guide Redis.

Profil prive et recuperation du compte

Toutes les routes ci-dessous utilisent le prefixe /api/mboka-services/v1. Les routes protegees exigent le Bearer Sanctum et une inscription deja verifiee. Elles ne permettent de gerer que le compte connecte.

Route Utilisation
GET /auth/profile Profil prive complet (egalement disponible dans /auth/me)
PATCH /auth/profile name, bio prestataire (500 caracteres max), avatar_media_id ou null
POST /auth/profile/contact-change Demander un OTP au nouveau contact, avec le mot de passe actuel
POST /auth/profile/contact-change/verify Confirmer le nouveau contact
PUT /auth/password Changer le mot de passe avec current_password
POST /auth/password/forgot Recuperation publique par un contact deja verifie
POST /auth/password/reset Nouveau mot de passe avec le code de recuperation
GET /auth/devices Lister ses tokens appareils sans leurs valeurs ni empreintes
DELETE /auth/devices/others Deconnecter les autres appareils

Modifier le profil et la photo

PATCH /auth/profile accepte par exemple {"name":"Jean Client"}, ou {"bio":"Electricien a Kinshasa"} pour un prestataire. Le nom est synchronise avec les profils client/prestataire. Les roles, points, notes, nombre de travaux et certifications sont proteges ; email, phone et password ne sont pas acceptes sur cette route. Le pays est celui choisi a l inscription ; les adresses restent gerees via /locations, et un changement de pays n est pas ajoute par ce module.

Pour une photo : envoyer d abord une image via POST /medias avec media_type=profile et le profil comme cible, puis PATCH /auth/profile avec {"avatar_media_id":ID_DU_MEDIA}. Seule une image de profil appartenant au compte est acceptee. null retire la selection sans supprimer le fichier ; supprimer le media via /medias retire automatiquement la selection. avatar_url apparait dans la reponse utilisateur. Les portfolios utilisent toujours le module medias existant.

Changer ou verifier un contact secondaire

POST /auth/profile/contact-change :

{"channel":"email","value":"nouveau@example.test","current_password":"MOT_DE_PASSE_ACTUEL"}

Pour un telephone, utiliser channel=sms et value au format international (le format local est normalise avec le pays du profil). Le contact actuel et son statut restent inchanges jusqu a validation. Le meme endpoint permet de confirmer un contact secondaire actuel qui n etait pas encore verifie.

POST /auth/profile/contact-change/verify :

{"channel":"email","verification_id":"UUID_RECU","code":"123456"}

Le code confirme seulement ce contact, sur ce compte. Il ne confirme pas l autre contact. Le changement ne modifie pas verification_channel choisi lors de l inscription. Un contact deja utilise par un autre compte est refuse, y compris si l autre compte l utilise apres la demande mais avant la confirmation. Les adresses e-mail sont normalisees en minuscules et leur unicite est protegee par un index PostgreSQL insensible a la casse.

Apres confirmation, tous les tokens sont revoques et data.reauthentication_required=true : se reconnecter via /auth/login avec le numero actuel ou l e-mail verifie, et le mot de passe. En cas de panne d envoi : 503, aucun changement applique. Pour renvoyer, repeter contact-change apres 60 secondes avec le mot de passe actuel.

Mot de passe oublie

POST /auth/password/forgot (sans Bearer) :

{"phone":"+243999000123","channel":"email"}

Le telephone local peut etre accompagne de country_id. On peut aussi identifier le compte directement par email, sans telephone. L envoi utilise exclusivement l e-mail deja verifie du compte (ou le telephone deja verifie si channel=sms), jamais une adresse fournie comme nouveau destinataire. Un compte dont aucun contact n est verifie doit d abord terminer son inscription.

HTTP 202 retourne success, message generique, verification_id opaque, channel, expires_in=300 et resend_after=60. La reponse a le meme format pour un compte inconnu, un contact non verifie, un quota compte atteint ou un echec d envoi : elle ne garantit pas qu un message est parti. Une panne du stockage OTP retourne 503 pour tous les comptes. Pour un renvoi, repeter la meme requete apres le delai ; conserver le nouveau verification_id. Les anciens identifiants deviennent invalides si un nouveau code est effectivement emis.

POST /auth/password/reset :

{"verification_id":"UUID_RECU","code":"123456","password":"NOUVEAU_MOT_DE_PASSE","password_confirmation":"NOUVEAU_MOT_DE_PASSE"}

Le nouveau mot de passe doit contenir au moins 8 caracteres. Le succes ne connecte pas automatiquement : il revoque tous les tokens, retourne reauthentication_required=true et exige /auth/login. Le code est utilisable une seule fois et aucun contact non verifie ne devient verifie. Pour changer le mot de passe en etant connecte, PUT /auth/password avec current_password, password et password_confirmation ; la meme reconnexion est ensuite requise.

Protection et stockage

Les OTP de recuperation et de contact sont separes des codes d inscription, lies au compte, au destinataire et a leur usage. Redis est le stockage temporaire par defaut ; OTP_CACHE_STORE=database reste un retour explicite possible. Seules des empreintes de codes sont stockees, jamais les mots de passe proposes ni les codes en clair. Les codes sont invalides apres 5 minutes. Trois erreurs bloquent 15 minutes ; les renvois ne remettent pas les echecs a zero. Maximum 3 envois par compte et par usage sur 15 minutes (tous canaux et IP confondus pour la recuperation). Les quotas peuvent survivre a une validation, sans conserver de code utilisable.

Les demandes partagent le limiteur IP OTP existant (10 demandes/15 minutes), et les verifications partagent 30 requetes/minute/IP. Les routes demandant le mot de passe actuel sont limitees a 3 reponses 422 par compte+IP sur 15 minutes, plus 30 requetes/minute/IP. Une reponse 429 contient Retry-After. Les mots de passe et tokens restent dans PostgreSQL ; /devices represente les tokens Sanctum, pas des sessions SPA. Leur duree d expiration n est pas modifiee par cette fonctionnalite.

Les e-mails de securite ont un objet et un contenu specifiques (recuperation ou confirmation de contact). Le meme SMTP Mailtrap Sandbox est utilise en developpement ; les tests automatises ne contactent ni Mailtrap ni Infobip. Les migrations ajoutent uniquement la reference de photo et l index d unicite d e-mail, sans confirmer de contact ni supprimer de compte. Un serveur ayant deja des e-mails dupliques, sans tenir compte de la casse, doit les faire corriger avant d appliquer l index.

Connexion et recuperation directement par e-mail

POST /auth/login accepte exactement un identifiant : {"email":"client@example.test","password":"MOT_DE_PASSE"} ou {"phone":"+243999000123","password":"MOT_DE_PASSE"}. Ne pas fournir les deux. L e-mail est normalise en minuscules et doit etre verifie pour servir a la connexion ; une inscription encore en attente retourne toujours son erreur de verification. Les 3 echecs/15 minutes par compte+IP sont partages entre son telephone et son e-mail pour eviter de contourner la limite en alternant les identifiants. La limite globale reste 30 requetes/minute/IP.

POST /auth/password/forgot accepte {"email":"client@example.test"} sans telephone : le canal par defaut devient email. Avec un telephone seul, le canal par defaut devient sms. channel peut etre indique explicitement pour choisir un autre contact deja verifie du meme compte. La reponse generique et /auth/password/reset restent identiques. Les deux identifiants fournis ensemble sont refuses.

Adresses privees et zones d intervention

Toutes les routes /locations et /provider-area exigent un token Sanctum et une inscription verifiee. GET /locations liste uniquement ses propres adresses. GET /locations/{location}, PUT et DELETE renvoient 404 pour une adresse appartenant a un autre compte, meme si son identifiant est connu. Le detail d une adresse n est plus public.

Carnet d adresses client

POST /locations enregistre une adresse ; PUT /locations/{location} remplace ses donnees. Exemple (remplacer les identifiants par ceux de votre pays et ville) :

{"country_id":7,"city_id":1,"label":"home","district":"Gombe","address":"Adresse de demonstration","instructions":"Indications privees","latitude":-4.32,"longitude":15.30,"is_default":true}

label est libre (80 caracteres maximum), district optionnel (160), address obligatoire (255), instructions privees optionnelles (1000). Latitude et longitude sont facultatives, mais doivent etre fournies ensemble ; valeurs admises : -90 a 90 et -180 a 180. La ville doit appartenir au pays, et le pays doit correspondre au profil. L application mobile ou web demande l autorisation GPS ; Laravel accepte aussi une adresse saisie manuellement.

La premiere adresse devient celle par defaut. PATCH /locations/{location}/default choisit une autre adresse. DELETE effectue une suppression logique et choisit la plus ancienne adresse restante comme remplacement, ou aucune s il n en reste plus. Modifier une adresse ne modifie pas les interventions deja creees. PUT est un remplacement : les champs optionnels omis sont effaces ou remis a leur valeur par defaut.

Zone du prestataire

Le prestataire utilise aussi /locations pour enregistrer ses adresses, puis GET /provider-area pour consulter sa configuration et PUT /provider-area pour la remplacer :

{"location_id":1,"work_mode":"both","intervention_radius_km":10,"publish_business_address":false}

location_id doit appartenir au prestataire et devient son adresse de reference. work_mode vaut on_site (chez le client), at_provider (dans son etablissement) ou both. Le rayon est obligatoire pour on_site et both : de 1 a 200 km. Sans GPS, le rayon ne peut pas etre controle automatiquement. coverage_configured dans les offres publiques indique si la configuration permet ce controle (ou si une adresse d etablissement est disponible en mode at_provider).

Les offres publiques exposent seulement le pays, la ville, le quartier, le mode et le rayon. L adresse exacte et le GPS restent prives. publish_business_address=true publie volontairement l adresse de l etablissement et ses coordonnees dans provider.area.business_address, uniquement pour at_provider ou both ; les instructions restent toujours privees. Modifier l adresse de reference, changer l adresse par defaut ou la supprimer retire cette publication : un nouvel accord explicite via PUT /provider-area est necessaire.

Adresse d une intervention

POST /service-requests accepte trois cas :

  • Chez le client (visit_mode=at_client par defaut) : location_id d une de ses adresses enregistrees.
  • Chez le client : location avec country_id, city_id, address et les champs facultatifs ci-dessus, sans location_id. Cette adresse ponctuelle n est pas ajoutee au carnet.
  • Chez le prestataire : visit_mode=at_provider et provider_id obligatoires, sans location ni location_id. L adresse de reference du prestataire est copiee.

Le service doit etre approuve. Un prestataire choisi doit proposer ce service avec availability_status=on et un mode compatible. Pour une intervention chez le client, si les deux lieux ont des coordonnees et si un rayon est configure, PostGIS controle la distance a vol d oiseau et refuse une demande hors zone (422). Sans coordonnees, la demande reste possible ; la couverture doit etre convenue avec le prestataire. approximate_distance_km vaut null si le calcul est impossible, sinon une distance arrondie au kilometre superieur (minimum 1), conservee avec la demande. Il ne s agit ni d une distance routiere ni d un temps de trajet.

Le lieu est une copie de l adresse au moment de la demande (ou du nouvel etablissement lors d une reaffectation en attente). Une modification ou suppression ulterieure de l adresse source ne change pas ce lieu historique. Le prestataire affecte voit seulement pays, ville et quartier avant acceptation pour une visite chez le client. Le client voit seulement cette zone avant acceptation pour une visite chez le prestataire. location.exact_location_visible indique si les champs exacts sont retournes. Apres acceptation, les deux participants voient l adresse, les instructions et le GPS ; apres annulation ou refus, seul le proprietaire du lieu et l administrateur les voient. Les autres comptes n ont pas acces a la demande.

Les adresses et copies historiques sont conservees dans PostgreSQL ; PostGIS calcule les distances. Redis n est pas utilise pour stocker ces adresses. Aucun suivi GPS continu ni endpoint de recherche de prestataires par distance n est ajoute dans cette etape.

Reprise des anciennes donnees

Les migrations attribuent les anciennes adresses aux comptes lies a leurs profils. Une adresse partagee par plusieurs comptes est copiee pour chacun ; une adresse sans proprietaire reste inaccessible via /locations. Les anciennes demandes recoivent une copie de l adresse actuellement presente en base : une ancienne adresse deja remplacee avant migration ne peut pas etre reconstituee. Les migrations ne suppriment aucune demande. Le retour arriere est refuse tant qu il existe des demandes sans adresse source ou des adresses sans GPS necessitant les nouvelles structures.

Fiche publique et profil professionnel du prestataire

GET /providers/{provider} retourne une fiche publique : nom, presentation, photo selectionnee, certification, verification du contact, services approuves avec tarifs et disponibilites, zone d intervention et reputation. provider designe l identifiant provider_profiles, pas celui du compte utilisateur. Les services indisponibles sont affiches avec availability_status=off ; seuls les services approuves figurent sur la fiche. Les montants utilisent le format decimal existant ; aucune conversion de devise n est ajoutee.

La fiche ne publie ni telephone, ni e-mail, ni adresse de reference privee. La zone respecte publish_business_address configure via /provider-area. Contact confirme par OTP et certification professionnelle sont deux informations distinctes ; cette fonctionnalite n ajoute pas un parcours de certification documentaire.

La reputation est calculee depuis les donnees : completed_interventions compte les interventions terminees ; rating et reviews_count portent sur les avis de 1 a 5 dont le client et le prestataire correspondent a une intervention terminee. Aucun avis donne rating=null et reviews_count=0. GET /providers/{provider}/reviews liste ces avis avec pagination, sans identifiant d intervention ni contacts. POST /service-requests/{service_request}/review permet au client de creer un avis unique apres confirmation de fin ; la modification des avis n est pas ajoutee.

GET /provider-profile, protege et reserve au prestataire, rassemble l apercu public, private_area, public_profile_url et completion. Le pourcentage de completion concerne photo, presentation, services, zone et au moins une publication personnelle publique ; ce pourcentage n est pas une certification. Les modifications utilisent les routes existantes /auth/profile, /provider-services et /provider-area.

Realisations photo et video

Les fichiers seuls ne sont jamais transformes automatiquement en publications. Les anciens portfolios restent inchanges et ne sont pas publies par cette migration. Une publication a un auteur, un prestataire concerne, un titre (120 caracteres), une description (5000), des fichiers ordonnes par ajout et un statut : draft, published ou hidden.

Creer et previsualiser

POST /publications exige un compte verifie client ou prestataire. Exemple prestataire :

{"title":"Installation terminee","description":"Presentation du resultat","service_id":1}

service_id est facultatif pour le prestataire et doit designer un service approuve de son offre. Son propre profil est toujours utilise ; provider_id et user_id ne sont pas acceptes.

Un client doit fournir service_request_id correspondant a sa propre intervention terminee. Le prestataire et le service sont derives de cette intervention, sans possibilite de les remplacer. Le prestataire peut aussi relier une realisation a une de ses interventions terminees. Exemple client :

{"title":"Resultat du depannage","description":"Le travail effectue chez moi","service_request_id":1}

HTTP 201 retourne data.publication avec status=draft. GET /publications/my liste uniquement ses publications, y compris brouillons et contenus masques. GET /publications/{publication} permet de previsualiser un brouillon avec le Bearer de son auteur (ou de l administrateur) ; les autres comptes et visiteurs recoivent 404.

Ajouter des photos et videos

POST /publications/{publication}/medias utilise multipart/form-data avec file. Maximum 10 fichiers par publication. Photos JPEG, PNG, WebP et GIF : 10 Mo maximum ; videos MP4, MOV et WebM : 100 Mo maximum. Les limites PHP, proxy et serveur doivent aussi autoriser la taille desiree. Les fichiers sont conserves dans leur format d origine : pas de transcodage ni de garantie de compatibilite des codecs ; les applications choisissent des formats lisibles sur leurs appareils.

Les fichiers sont stockes sur le disque prive publication (storage/app/publications), sans lien public storage. Les reponses exposent uniquement id, file_type, mime_type, file_size et url ; ni chemin local, ni nom original. GET /publications/{publication}/medias/{media} sert un fichier avec controle de visibilite et Cache-Control private/no-store. Pour previsualiser un fichier prive, l application doit envoyer le Bearer sur cette requete aussi. Le serveur accepte les lectures par plages pour la lecture video.

Les routes generiques PUT/DELETE /medias/{media} refusent les fichiers de publication : utiliser DELETE /publications/{publication}/medias/{media}. Des pieces jointes privees d intervention ne sont pas reutilisees ou publiees automatiquement. Verifier le contenu des images/videos avant publication, y compris les personnes, adresses et metadonnees eventuelles : les fichiers originaux ne sont pas nettoyes automatiquement.

Publier ou modifier

Apres previsualisation, PATCH /publications/{publication} :

{"status":"published","publication_consent":true}

Cette confirmation signifie que l auteur choisit de rendre le contenu public et dispose des autorisations necessaires. Au moins un fichier est obligatoire. Une publication client reste liee a son intervention terminee. Sans confirmation explicite, rien n est publie.

Modifier title ou description sans demander explicitement une nouvelle publication remet le contenu en brouillon. Ajouter ou retirer un fichier le remet egalement en brouillon. Les anciennes URLs de fichiers sont alors inaccessibles aux visiteurs. PATCH avec status=draft retire volontairement du public. DELETE /publications/{publication} supprime logiquement la publication et ferme aussi ses routes de fichiers ; les fichiers restent en stockage prive pour le moment, sans purge automatique. Une copie deja telechargee par un visiteur ne peut pas etre rappelee.

Le lien a l intervention, au prestataire, au service et a l auteur est immuable apres creation. Les interventions liees ne peuvent pas etre supprimees physiquement tant que ces publications existent ; leur suppression logique reste disponible.

Consulter les realisations

GET /providers/{provider}/publications liste uniquement les contenus publics avec pagination (per_page de 1 a 50, 15 par defaut). Filtres facultatifs : author_role=provider|client et file_type=image|video. Un contenu avec photos et videos apparait dans les deux filtres. La liste peut etre vide. La fiche fournit publications_url pour charger cette zone separement, sans charger toutes les videos avec le profil.

L auteur est identifie par son nom, sa photo et son role. verified_intervention indique un rattachement a une intervention terminee, pas une certification du contenu. Les identifiants d intervention sont reserves a l auteur et a l administrateur ; les adresses d intervention et contacts ne figurent jamais dans la publication.

Signalement et moderation

POST /publications/{publication}/report avec {"reason":"Motif du signalement"} exige un compte verifie et une publication publique. Un seul signalement par compte et publication, remplace si repete. L auteur ne signale pas son propre contenu. Le prestataire peut signaler une publication de client, mais ne peut pas la modifier ou la supprimer. Un signalement ne masque pas automatiquement le contenu.

Les administrateurs consultent GET /publications/reports (pagination des publications, jusqu a 20 motifs recents par publication). PATCH /publications/{publication}/moderation accepte {"action":"hide"} pour masquer ou {"action":"restore"} pour rendre le contenu a son auteur en brouillon. Un contenu masque ne peut pas etre republie ou voir ses fichiers modifies par son auteur. Celui-ci peut toujours le supprimer. Une restauration ne publie jamais automatiquement : une nouvelle confirmation de l auteur est necessaire. Les signalements restent conserves pour le suivi.

Demande, messagerie, accord et confirmation de fin

Ce parcours remplace l acceptation simple par le prestataire. Toutes les routes suivantes exigent un compte verifie et son Bearer Sanctum. Un administrateur peut consulter le dossier et traiter un probleme, mais ne confirme pas un prix ou une fin a la place du client.

Envoyer la demande

POST /service-requests conserve service_id, description (5000 caracteres maximum), provider_id et l adresse enregistree ou ponctuelle deja documentee. scheduled_date est maintenant facultatif : avant accord, il ne s agit que d une preference. Une demande sans prestataire conserve conversation_id=null ; affecter le prestataire avec PATCH /service-requests/{service_request}/assign-provider ouvre la conversation. Une demande envoyee a un prestataire ouvre sa conversation des sa creation. Les demandes de son propre profil prestataire sont refusees.

GET /service-requests/{service_request}/conversations liste les conversations du dossier (20 par page). Le client et l administrateur peuvent consulter les archives. En cas de reaffectation en discussion, une nouvelle conversation est creee et les anciennes propositions sont retirees. Le nouveau prestataire ne voit pas les anciens echanges ; l ancien prestataire perd l acces au dossier et aux fichiers de conversation. Le client conserve son historique en lecture seule. Aucune reaffectation n est possible apres accord.

Echanger des messages et des fichiers

  • GET /conversations/{conversation}/messages : historique, du plus recent au plus ancien, 30 messages par page (per_page de 1 a 100).
  • GET avec after_id=ID : messages plus recents que cet identifiant, en ordre croissant. Utile pour interroger regulierement depuis React ou React Native. Il n y a pas encore de WebSocket ni de notification push externe.
  • POST sur la meme route : body (5000 caracteres maximum), files[], ou les deux. Pour des fichiers utiliser multipart/form-data. Maximum 5 fichiers par message : photos 10 Mo et videos 100 Mo, formats JPEG/PNG/WebP/GIF/MP4/MOV/WebM. Au moins du texte ou un fichier est obligatoire.
  • PATCH /conversations/{conversation}/read avec {"last_message_id":ID} : marquer les messages comme lus. L identifiant doit appartenir a cette conversation et le compteur ne recule pas.

Les changements d etat ajoutent des messages systeme non falsifiables, avec event et metadata. unread_count compte seulement les messages utilisateur recus, pas les evenements systeme. Les participants recoivent des notifications en base pour les messages et etapes importantes, sans recopier le texte prive dans la notification. L historique ne se modifie pas via les routes medias.

Les fichiers de conversation utilisent GET /conversations/{conversation}/files/{media}. Leur stockage est prive, sans URL storage publique. Le Bearer doit etre envoye aussi pour charger une image ou lire une video ; le serveur accepte les lectures par plages. Les refus, annulations et interventions terminees rendent la conversation en lecture seule, mais les participants conservant l acces peuvent lire l historique.

Les pieces jointes initiales a la demande restent envoyees via POST /medias avec mediable_type=service_request et media_type=attachment. Elles sont desormais stockees en prive et listees par GET /service-requests/{service_request}/attachments (30 par page). Les URL de fichiers exigent les memes droits que la demande. Une piece jointe ne peut pas etre deplacee vers un profil public. Les pieces jointes d un dossier restent visibles aux participants actuels ; les fichiers des messages, eux, restent isoles dans leur conversation d origine.

Convenir du prix et du rendez-vous

Le prestataire envoie POST /service-requests/{service_request}/proposals :

{"price":"25.00","currency":"USD","terms":"Diagnostic et reparation au prix convenu.","appointment_mode":"now","arrival_minutes":45}

Le prix est fixe pour cette intervention : de 0 a 9999999999.99, au maximum 2 decimales. Devises actuellement acceptees : USD et CDF. Aucun paiement ni conversion de devise n est effectue. terms decrit le travail convenu, 3000 caracteres maximum.

now signifie disponible maintenant, avec une arrivee estimee de 1 a 240 minutes apres confirmation du client. Ce n est pas une promesse d arrivee immediate. Pour un rendez-vous programme :

{"price":"25.00","currency":"USD","terms":"Diagnostic et reparation au prix convenu.","appointment_mode":"scheduled","scheduled_date":"2027-01-20T09:00:00+01:00"}

Utiliser une date future ISO 8601 avec fuseau explicite (Z ou decalage). Les dates sont stockees et retournees en UTC. Pour scheduled, arrival_minutes est ignore ; pour now, scheduled_date est ignore.

Le statut passe a proposed. La proposition now expire apres 15 minutes ; une proposition scheduled apres 24 heures, ou au rendez-vous si celui-ci arrive avant. Une nouvelle proposition pendant la discussion remplace la precedente. GET /service-requests/{service_request}/proposals donne l historique de la conversation actuelle, 20 propositions par page.

Le client confirme avec PATCH /service-requests/{service_request}/proposals/{proposal}/confirm, ou refuse avec /decline. Seule une proposition encore active, de la conversation actuelle et non expiree peut etre confirmee. Le refus ramene a pending pour poursuivre la discussion. Le prix, la devise, la proposition retenue et le rendez-vous sont alors enregistres dans agreement ; accepted signifie que les deux parties sont engagees. L adresse exacte est partagee a cet accord, pas au simple envoi d une proposition.

Il n y a aucun mecanisme de supplement, de modification du montant ou de remplacement du rendez-vous apres accord. Un nouveau besoin exige une nouvelle demande. L ancien PATCH /service-requests/{service_request}/accept est conserve comme alias de proposition avec les memes champs obligatoires ; il ne permet plus de sauter la confirmation du client.

Realiser et terminer

  1. Le prestataire appelle PATCH /service-requests/{service_request}/start : accepted -> in_progress. Le demarrage est manuel, pas declenche automatiquement par l heure du rendez-vous. Pour scheduled, il est refuse avant l heure convenue ; pour now, l arrivee reste une estimation et le prestataire peut demarrer en arrivant avant cette estimation.
  2. Apres le travail, il appelle PATCH /service-requests/{service_request}/complete, avec note facultative (5000 caracteres). Le statut devient awaiting_confirmation, pas completed.
  3. Le client appelle PATCH /service-requests/{service_request}/confirm-completion pour confirmer : le statut devient completed.
  4. Il peut ensuite creer son avis unique avec POST /service-requests/{service_request}/review et {"rating":5,"comment":"Travail satisfaisant"}. La note doit etre de 1 a 5 ; le commentaire est obligatoire, 3000 caracteres maximum. L avis est public sur la fiche. Le prestataire et les autres clients ne peuvent pas noter cette intervention.
  5. Les publications de realisation liees a ce dossier deviennent possibles selon le parcours de publication volontaire existant. Les fichiers de la messagerie ne deviennent jamais publics automatiquement.

Le prestataire peut refuser une demande pending ou proposed via /reject. Le client peut annuler pending, proposed ou accepted via /cancel, avec reason facultatif (3000 caracteres). Une intervention en cours ne se termine ni ne s annule par ce raccourci.

Signaler un probleme

Depuis awaiting_confirmation, le client envoie POST /service-requests/{service_request}/issues avec {"reason":"Le probleme persiste"}. Le statut devient disputed, sans ouvrir les avis et publications lies a une intervention terminee. La conversation reste ouverte pour echanger et joindre des fichiers.

GET /intervention-follow-ups est reserve aux administrateurs. PATCH /service-requests/{service_request}/issues/resolve demande action=resume_work ou cancel et resolution obligatoire (3000 caracteres). resume_work permet au prestataire de reprendre puis de declarer a nouveau la fin, au meme prix convenu. cancel ferme l intervention sans la compter comme terminee. La resolution et son auteur sont conserves. Si le probleme a ete regle entre les parties, le client peut aussi confirmer explicitement la fin depuis disputed ; cela resout le signalement et termine l intervention. Un administrateur ne force pas une bonne note ou une confirmation client.

Rappels et suivi

php artisan interventions:maintain expire les propositions, rappelle le client apres 24 heures sans confirmation et marque le dossier pour suivi administrateur apres 72 heures. Chaque rappel/escalade n est emis qu une fois par declaration de fin. Le silence ne termine pas le travail, ne genere pas d avis et ne confirme aucun prix.

La commande est planifiee toutes les heures dans le scheduler Laravel. En local, php artisan schedule:work permet de le faire tourner ; en production, configurer l execution reguliere de php artisan schedule:run. Aucun worker Horizon n est necessaire : les notifications sont conservees directement en PostgreSQL. Les durees sont definies dans config/interventions.php. Sans scheduler, le controle d expiration a la confirmation reste effectif, mais les rappels et mises a jour automatiques des statuts expires ne s executent pas.

Anciennes demandes et fichiers

La migration conserve les statuts et dates existants et cree les conversations des demandes deja affectees. Aucun prix historique n est invente. agreement.legacy=true identifie une ancienne demande sans proposition enregistree. Une ancienne intervention deja accepted ou in_progress peut continuer, mais toute nouvelle declaration de fin attend desormais la confirmation du client. Les anciens dossiers completed restent termines.

Pour les anciennes pieces jointes stockees sur le disque public, executer d abord php artisan media:privatize-interventions --dry-run, puis sans --dry-run. La commande copie, compare les empreintes et bascule le media avant de retirer la copie publique apres validation. Elle est repetable, refuse les chemins non reconnus et ne remplace pas une copie privee differente. En cas d erreur, corriger le fichier concerne et relancer ; les sources ne sont pas supprimees avant verification. Le retrait d une URL publique ne peut pas rappeler des copies deja telechargees.

La migration ne supprime aucun message ni ancienne demande. Son retour arriere est refuse si des messages, propositions, problemes, nouveaux statuts ou fichiers prives necessitent une reprise explicite des donnees.
