Utiliser l API Mboka Services

L API connecte clients et prestataires locaux. Son prefixe est /api/mboka-services/v1.

Faire une premiere requete

Demarrer PostgreSQL, Redis pour les OTP, puis Laravel depuis le dossier du projet :

powershell -NoProfile -ExecutionPolicy Bypass -File scripts/postgres.ps1 start
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/redis.ps1 start
php artisan serve

Consulter le catalogue public :

GET http://127.0.0.1:8000/api/mboka-services/v1/categories
Accept: application/json
X-Locale: fr

Les langues disponibles sont fr, en et ln. Le fichier openapi.json est importable directement dans Postman : Import > fichier ou URL du fichier OpenAPI de la documentation.

Authentification mobile et web

L implementation actuelle utilise des tokens Bearer Sanctum, sur mobile comme sur le web. POST /auth/register cree un compte en attente et retourne HTTP 202 avec data.verification_id, expires_in et resend_after, sans token. POST /auth/otp/verify confirme le contact choisi (SMS ou e-mail) et retourne un token dans data.token. Les connexions suivantes par POST /auth/login utilisent telephone ou e-mail verifie + mot de passe et retournent un token si le contact choisi est deja verifie. Pour les routes protegees :

Authorization: Bearer VOTRE_TOKEN
Accept: application/json

Le mot de passe d un compte est hache dans PostgreSQL. L empreinte du token est conservee dans personal_access_tokens. POST /auth/logout revoque le token courant. Redis ne remplace pas ce stockage.

GET /auth/me retourne le compte connecte. Les comptes client et provider peuvent s inscrire ; les droits administrateur ne sont pas accessibles par inscription publique.

Valider l inscription par OTP SMS ou e-mail

  1. Appeler POST /auth/register avec les champs habituels du compte et verification_channel=sms ou email. Par defaut : sms. Le telephone et le pays restent requis ; l e-mail est obligatoire pour le canal email.
  2. Conserver data.verification_id de la reponse HTTP 202.
  3. Recevoir le code sur le canal choisi (dans Mailtrap pour les tests e-mail), puis envoyer les donnees suivantes :
POST /api/mboka-services/v1/auth/otp/verify
Content-Type: application/json

{
  "verification_id": "UUID_RECU_A_L_INSCRIPTION",
  "code": "123456"
}

Le code doit etre une chaine de 6 chiffres. Il expire apres 5 minutes. Apres 3 codes incorrects, verification et renvoi sont bloques pendant 15 minutes. Le code est consomme une seule fois ; le succes renseigne phone_verified_at pour sms ou email_verified_at pour email, sans confirmer l autre contact, et retourne un token Sanctum. Les anciens tokens du compte sont revoques.

Pour renvoyer, appeler POST /auth/otp/resend avec verification_id, apres 60 secondes. Maximum 3 envois par compte sur 15 minutes et 10 demandes par IP sur 15 minutes, inscription et renvoi cumules. Le renvoi invalide l ancien code, sans remettre les echecs a zero. Un echec Infobip ou SMTP consomme aussi un essai d envoi pour eviter les boucles de facturation.

Les comptes deja presents restent non verifies apres migration. Avec le bon mot de passe, POST /auth/login retourne HTTP 403, error_code=phone_verification_required (ou email_verification_required pour les nouvelles inscriptions par e-mail), data.channel et data.verification_id pour reprendre le parcours. Aucun token n est delivre avant verification. Les anciens tokens ne donnent pas acces aux routes metier protegees tant que le contact choisi n est pas verifie ; logout reste possible.

Si l envoi echoue, HTTP 503 retourne verification_id lorsque le compte a ete cree. Le compte n est pas supprime : reprendre avec resend apres le delai indique. Un code perdu ou expire exige un renvoi.

Limites de connexion

POST /auth/login autorise 3 echecs par compte + IP (telephone et e-mail partages) sur une fenetre de 15 minutes qui commence au premier echec. Les connexions reussies ne consomment pas ces essais. La quatrieme tentative est refusee jusqu a expiration de la fenetre, meme avec un mot de passe correct. Il existe aussi une limite de 30 requetes/minute par IP, tous numeros confondus.

En cas de blocage : HTTP 429 avec success=false, message, retry_after et en-tete Retry-After. Attendre ce delai avant de reessayer. Les memes compteurs sont utilises par le mobile et le web. PostgreSQL est le stockage par defaut ; Redis est activable par configuration.

Service, ProviderService et ServiceRequest representent respectivement un metier, une offre commerciale et une intervention demandee.

Parcours d une intervention

  1. Le client cree son compte et sa localisation.
  2. Il choisit un service approuve et cree une demande.
  3. Il peut choisir un prestataire immediatement ou l affecter plus tard.
  4. Le prestataire discute puis propose un prix et un rendez-vous ; le client confirme ou refuse.
  5. Le travail demarre, le prestataire declare la fin puis le client la confirme ou signale un probleme.

Statuts du parcours actuel : pending -> proposed -> accepted -> in_progress -> awaiting_confirmation -> completed. Le client confirme la proposition puis la fin ; un probleme donne disputed. Le refus donne rejected, l annulation cancelled. Voir le parcours detaille ci-dessous.

Fichiers et erreurs

Pour les medias, utiliser multipart/form-data avec file, mediable_type, mediable_id et media_type. Une photo de profil doit etre une image. Les images de profil et anciens portfolios utilisent le disque public. Les fichiers des publications et des interventions utilisent des disques prives et des routes de consultation controlees. Les limites dependent de leur usage et des limites PHP/serveur.

Les erreurs 401 indiquent une authentification manquante ou invalide ; 403 une action interdite ; 422 une validation ou regle metier non respectee ; 429 un depassement des limites. Si Redis est configure puis inaccessible, une erreur de connexion Predis est rendue en 503.

Configurer Infobip et tester sans SMS reel

Par defaut, SMS_DRIVER=fake ne contacte aucun prestataire. En local, le dernier SMS de chaque verification est ecrit dans .local/sms-outbox/<verification_id>.json. Lire ce fichier prive pour recuperer le code, puis tester verify dans Postman. Ce dossier est ignore par Git. Les tests automatises capturent les messages en memoire. Le mode fake est refuse en production.

Pour activer de vrais SMS, renseigner uniquement dans le .env prive :

SMS_DRIVER=infobip
INFOBIP_BASE_URL=https://VOTRE_COMPTE.api.infobip.com
INFOBIP_API_KEY=VOTRE_CLE_PRIVEE
INFOBIP_SENDER=VOTRE_EXPEDITEUR_AUTORISE

Puis executer php artisan config:clear. Le compte Infobip doit autoriser les SMS et l expediteur choisi. La cle reste cote Laravel. L API utilise /sms/3/messages avec Authorization: App, et distingue un message accepte d une livraison effectivement recue. Un compte d essai peut limiter les destinataires aux numeros verifies chez Infobip.

Les codes ne sont jamais retournes dans les reponses API ni ecrits dans les journaux applicatifs. Seul le mode simule local possede une boite SMS privee contenant le texte du message. Ne pas utiliser cette simulation en production.

Les tests automatises utilisent des reponses HTTP simulees et n envoient aucun SMS.

OTP e-mail avec Mailtrap Sandbox

Mailtrap Sandbox capture les courriels de developpement : ils apparaissent dans son interface, pas dans la boite mail reelle du destinataire. Creer un sandbox dans Mailtrap, ouvrir son onglet Integration, selectionner SMTP/Laravel et copier les identifiants uniquement dans le fichier .env prive :

MAIL_MAILER=smtp
OTP_MAILER=smtp
MAIL_SCHEME=smtp
MAIL_HOST=sandbox.smtp.mailtrap.io
MAIL_PORT=2525
MAIL_USERNAME=IDENTIFIANT_DU_SANDBOX
MAIL_PASSWORD=MOT_DE_PASSE_DU_SANDBOX
MAIL_FROM_ADDRESS=noreply@mboka.test
MAIL_FROM_NAME="Mboka Services"
MAIL_TIMEOUT=10

Executer ensuite php artisan config:clear. MAIL_SCHEME=smtp autorise la negociation STARTTLS du transport Symfony ; la verification des certificats reste active. Sur ce poste Windows, si PHP ne trouve pas les certificats racines, configurer curl.cainfo et openssl.cafile dans le php.ini avec le fichier de certificats Laragon.

Exemple Postman, POST /api/mboka-services/v1/auth/register (remplacer country_id par celui retourne par GET /countries et utiliser un nouveau numero) :

{
  "name": "Client Mailtrap",
  "country_id": 7,
  "phone": "0999000123",
  "email": "client@example.test",
  "verification_channel": "email",
  "password": "password",
  "password_confirmation": "password",
  "account_type": "client"
}

La reponse 202 contient data.channel=email, verification_id, expires_in et resend_after. Copier le code a six chiffres affiche dans Mailtrap et appeler /auth/otp/verify avec verification_id et code (chaine). Le token recu permet /auth/me et les routes metier. email_verified_at est renseigne, phone_verified_at reste null. La connexion suivante accepte telephone ou e-mail verifie, avec le mot de passe.

/auth/otp/resend utilise le canal enregistre lors de l inscription : aucun changement de canal ni de destinataire n est autorise par cette route. Les comptes existants gardent sms ; cette evolution ne confirme pas leurs contacts automatiquement. Les comptes ayant deja un numero doivent reprendre leur verification existante.

Les limites et le stockage OTP optionnel Redis sont communs aux deux canaux : 5 minutes, 3 erreurs puis 15 minutes de blocage, renvoi apres 60 secondes, 3 envois/15 minutes par compte. L envoi est synchrone et ne necessite aucun worker. Une panne SMTP retourne 503 et conserve le compte en attente avec verification_id ; apres correction, reprendre avec resend sans recreer le compte. Les transports log/array/failover sont refuses pour les OTP e-mail afin de ne pas journaliser les codes ni annoncer un envoi fictif. Le message existe en HTML et texte, localise via X-Locale.

En production, remplacer les identifiants du Sandbox par ceux d un service d envoi reel, avec un expediteur et un domaine autorises. Le Sandbox n est pas un service de livraison vers les utilisateurs.

References : integration SMTP Mailtrap, Email Sandbox.

Le stockage OTP est maintenant Redis par defaut (OTP_CACHE_STORE=otp, base 3), pour les SMS comme pour les e-mails. Les comptes, les validations et les tokens Sanctum restent en PostgreSQL. Redis indisponible implique un refus temporaire HTTP 503, sans basculement silencieux. Les anciens codes PostgreSQL ne sont pas transferes ; demander un nouveau code apres le changement de stockage. Voir le guide Redis.

Toutes les routes ci-dessous utilisent le prefixe /api/mboka-services/v1. Les routes protegees exigent le Bearer Sanctum et une inscription deja verifiee. Elles ne permettent de gerer que le compte connecte.

Modifier le profil et la photo

PATCH /auth/profile accepte par exemple {"name":"Jean Client"}, ou {"bio":"Electricien a Kinshasa"} pour un prestataire. Le nom est synchronise avec les profils client/prestataire. Les roles, points, notes, nombre de travaux et certifications sont proteges ; email, phone et password ne sont pas acceptes sur cette route. Le pays est celui choisi a l inscription ; les adresses restent gerees via /locations, et un changement de pays n est pas ajoute par ce module.

Pour une photo : envoyer d abord une image via POST /medias avec media_type=profile et le profil comme cible, puis PATCH /auth/profile avec {"avatar_media_id":ID_DU_MEDIA}. Seule une image de profil appartenant au compte est acceptee. null retire la selection sans supprimer le fichier ; supprimer le media via /medias retire automatiquement la selection. avatar_url apparait dans la reponse utilisateur. Les portfolios utilisent toujours le module medias existant.

Changer ou verifier un contact secondaire

POST /auth/profile/contact-change :

{"channel":"email","value":"nouveau@example.test","current_password":"MOT_DE_PASSE_ACTUEL"}

Pour un telephone, utiliser channel=sms et value au format international (le format local est normalise avec le pays du profil). Le contact actuel et son statut restent inchanges jusqu a validation. Le meme endpoint permet de confirmer un contact secondaire actuel qui n etait pas encore verifie.

POST /auth/profile/contact-change/verify :

{"channel":"email","verification_id":"UUID_RECU","code":"123456"}

Le code confirme seulement ce contact, sur ce compte. Il ne confirme pas l autre contact. Le changement ne modifie pas verification_channel choisi lors de l inscription. Un contact deja utilise par un autre compte est refuse, y compris si l autre compte l utilise apres la demande mais avant la confirmation. Les adresses e-mail sont normalisees en minuscules et leur unicite est protegee par un index PostgreSQL insensible a la casse.

Apres confirmation, tous les tokens sont revoques et data.reauthentication_required=true : se reconnecter via /auth/login avec le numero actuel ou l e-mail verifie, et le mot de passe. En cas de panne d envoi : 503, aucun changement applique. Pour renvoyer, repeter contact-change apres 60 secondes avec le mot de passe actuel.

Mot de passe oublie

POST /auth/password/forgot (sans Bearer) :

{"phone":"+243999000123","channel":"email"}

Le telephone local peut etre accompagne de country_id. On peut aussi identifier le compte directement par email, sans telephone. L envoi utilise exclusivement l e-mail deja verifie du compte (ou le telephone deja verifie si channel=sms), jamais une adresse fournie comme nouveau destinataire. Un compte dont aucun contact n est verifie doit d abord terminer son inscription.

HTTP 202 retourne success, message generique, verification_id opaque, channel, expires_in=300 et resend_after=60. La reponse a le meme format pour un compte inconnu, un contact non verifie, un quota compte atteint ou un echec d envoi : elle ne garantit pas qu un message est parti. Une panne du stockage OTP retourne 503 pour tous les comptes. Pour un renvoi, repeter la meme requete apres le delai ; conserver le nouveau verification_id. Les anciens identifiants deviennent invalides si un nouveau code est effectivement emis.

POST /auth/password/reset :

{"verification_id":"UUID_RECU","code":"123456","password":"NOUVEAU_MOT_DE_PASSE","password_confirmation":"NOUVEAU_MOT_DE_PASSE"}

Le nouveau mot de passe doit contenir au moins 8 caracteres. Le succes ne connecte pas automatiquement : il revoque tous les tokens, retourne reauthentication_required=true et exige /auth/login. Le code est utilisable une seule fois et aucun contact non verifie ne devient verifie. Pour changer le mot de passe en etant connecte, PUT /auth/password avec current_password, password et password_confirmation ; la meme reconnexion est ensuite requise.

Protection et stockage

Les OTP de recuperation et de contact sont separes des codes d inscription, lies au compte, au destinataire et a leur usage. Redis est le stockage temporaire par defaut ; OTP_CACHE_STORE=database reste un retour explicite possible. Seules des empreintes de codes sont stockees, jamais les mots de passe proposes ni les codes en clair. Les codes sont invalides apres 5 minutes. Trois erreurs bloquent 15 minutes ; les renvois ne remettent pas les echecs a zero. Maximum 3 envois par compte et par usage sur 15 minutes (tous canaux et IP confondus pour la recuperation). Les quotas peuvent survivre a une validation, sans conserver de code utilisable.

Les demandes partagent le limiteur IP OTP existant (10 demandes/15 minutes), et les verifications partagent 30 requetes/minute/IP. Les routes demandant le mot de passe actuel sont limitees a 3 reponses 422 par compte+IP sur 15 minutes, plus 30 requetes/minute/IP. Une reponse 429 contient Retry-After. Les mots de passe et tokens restent dans PostgreSQL ; /devices represente les tokens Sanctum, pas des sessions SPA. Leur duree d expiration n est pas modifiee par cette fonctionnalite.

Les e-mails de securite ont un objet et un contenu specifiques (recuperation ou confirmation de contact). Le meme SMTP Mailtrap Sandbox est utilise en developpement ; les tests automatises ne contactent ni Mailtrap ni Infobip. Les migrations ajoutent uniquement la reference de photo et l index d unicite d e-mail, sans confirmer de contact ni supprimer de compte. Un serveur ayant deja des e-mails dupliques, sans tenir compte de la casse, doit les faire corriger avant d appliquer l index.

Connexion et recuperation directement par e-mail

POST /auth/login accepte exactement un identifiant : {"email":"client@example.test","password":"MOT_DE_PASSE"} ou {"phone":"+243999000123","password":"MOT_DE_PASSE"}. Ne pas fournir les deux. L e-mail est normalise en minuscules et doit etre verifie pour servir a la connexion ; une inscription encore en attente retourne toujours son erreur de verification. Les 3 echecs/15 minutes par compte+IP sont partages entre son telephone et son e-mail pour eviter de contourner la limite en alternant les identifiants. La limite globale reste 30 requetes/minute/IP.

POST /auth/password/forgot accepte {"email":"client@example.test"} sans telephone : le canal par defaut devient email. Avec un telephone seul, le canal par defaut devient sms. channel peut etre indique explicitement pour choisir un autre contact deja verifie du meme compte. La reponse generique et /auth/password/reset restent identiques. Les deux identifiants fournis ensemble sont refuses.

Adresses privees et zones d intervention

Toutes les routes /locations et /provider-area exigent un token Sanctum et une inscription verifiee. GET /locations liste uniquement ses propres adresses. GET /locations/{location}, PUT et DELETE renvoient 404 pour une adresse appartenant a un autre compte, meme si son identifiant est connu. Le detail d une adresse n est plus public.

Carnet d adresses client

POST /locations enregistre une adresse ; PUT /locations/{location} remplace ses donnees. Exemple (remplacer les identifiants par ceux de votre pays et ville) :

{"country_id":7,"city_id":1,"label":"home","district":"Gombe","address":"Adresse de demonstration","instructions":"Indications privees","latitude":-4.32,"longitude":15.30,"is_default":true}

label est libre (80 caracteres maximum), district optionnel (160), address obligatoire (255), instructions privees optionnelles (1000). Latitude et longitude sont facultatives, mais doivent etre fournies ensemble ; valeurs admises : -90 a 90 et -180 a 180. La ville doit appartenir au pays, et le pays doit correspondre au profil. L application mobile ou web demande l autorisation GPS ; Laravel accepte aussi une adresse saisie manuellement.

La premiere adresse devient celle par defaut. PATCH /locations/{location}/default choisit une autre adresse. DELETE effectue une suppression logique et choisit la plus ancienne adresse restante comme remplacement, ou aucune s il n en reste plus. Modifier une adresse ne modifie pas les interventions deja creees. PUT est un remplacement : les champs optionnels omis sont effaces ou remis a leur valeur par defaut.

Zone du prestataire

Le prestataire utilise aussi /locations pour enregistrer ses adresses, puis GET /provider-area pour consulter sa configuration et PUT /provider-area pour la remplacer :

{"location_id":1,"work_mode":"both","intervention_radius_km":10,"publish_business_address":false}

location_id doit appartenir au prestataire et devient son adresse de reference. work_mode vaut on_site (chez le client), at_provider (dans son etablissement) ou both. Le rayon est obligatoire pour on_site et both : de 1 a 200 km. Sans GPS, le rayon ne peut pas etre controle automatiquement. coverage_configured dans les offres publiques indique si la configuration permet ce controle (ou si une adresse d etablissement est disponible en mode at_provider).

Les offres publiques exposent seulement le pays, la ville, le quartier, le mode et le rayon. L adresse exacte et le GPS restent prives. publish_business_address=true publie volontairement l adresse de l etablissement et ses coordonnees dans provider.area.business_address, uniquement pour at_provider ou both ; les instructions restent toujours privees. Modifier l adresse de reference, changer l adresse par defaut ou la supprimer retire cette publication : un nouvel accord explicite via PUT /provider-area est necessaire.

Adresse d une intervention

POST /service-requests accepte trois cas :

  • Chez le client (visit_mode=at_client par defaut) : location_id d une de ses adresses enregistrees.
  • Chez le client : location avec country_id, city_id, address et les champs facultatifs ci-dessus, sans location_id. Cette adresse ponctuelle n est pas ajoutee au carnet.
  • Chez le prestataire : visit_mode=at_provider et provider_id obligatoires, sans location ni location_id. L adresse de reference du prestataire est copiee.

Le service doit etre approuve. Un prestataire choisi doit proposer ce service avec availability_status=on et un mode compatible. Pour une intervention chez le client, si les deux lieux ont des coordonnees et si un rayon est configure, PostGIS controle la distance a vol d oiseau et refuse une demande hors zone (422). Sans coordonnees, la demande reste possible ; la couverture doit etre convenue avec le prestataire. approximate_distance_km vaut null si le calcul est impossible, sinon une distance arrondie au kilometre superieur (minimum 1), conservee avec la demande. Il ne s agit ni d une distance routiere ni d un temps de trajet.

Le lieu est une copie de l adresse au moment de la demande (ou du nouvel etablissement lors d une reaffectation en attente). Une modification ou suppression ulterieure de l adresse source ne change pas ce lieu historique. Le prestataire affecte voit seulement pays, ville et quartier avant acceptation pour une visite chez le client. Le client voit seulement cette zone avant acceptation pour une visite chez le prestataire. location.exact_location_visible indique si les champs exacts sont retournes. Apres acceptation, les deux participants voient l adresse, les instructions et le GPS ; apres annulation ou refus, seul le proprietaire du lieu et l administrateur les voient. Les autres comptes n ont pas acces a la demande.

Les adresses et copies historiques sont conservees dans PostgreSQL ; PostGIS calcule les distances. Redis n est pas utilise pour stocker ces adresses. Aucun suivi GPS continu ni endpoint de recherche de prestataires par distance n est ajoute dans cette etape.

Reprise des anciennes donnees

Les migrations attribuent les anciennes adresses aux comptes lies a leurs profils. Une adresse partagee par plusieurs comptes est copiee pour chacun ; une adresse sans proprietaire reste inaccessible via /locations. Les anciennes demandes recoivent une copie de l adresse actuellement presente en base : une ancienne adresse deja remplacee avant migration ne peut pas etre reconstituee. Les migrations ne suppriment aucune demande. Le retour arriere est refuse tant qu il existe des demandes sans adresse source ou des adresses sans GPS necessitant les nouvelles structures.

Recherche de prestataires par localisation

GET /providers est protege par Bearer Sanctum et verification de l inscription. Il retourne data.providers et meta.search avec les filtres effectivement appliques, sans changer le profil du client.

Ordre de priorite geographique :

  1. city_id et/ou district choisis manuellement : ils remplacent la recherche GPS. Un quartier seul utilise la ville de l adresse par defaut du client.
  2. Sans choix geographique manuel, use_location=true avec latitude et longitude : utiliser la position actuelle autorisee.
  3. Sinon, utiliser automatiquement la ville de l adresse par defaut du profil client (customer_profiles.location_id). Cette adresse doit etre active et appartenir au client ; ses coordonnees enregistrees ne sont jamais reutilisees pour contourner un refus GPS.
  4. Sans position ni ville de profil valide, repondre 422 avec errors.city_id : afficher un choix de ville dans l application.

React/React Native gere la permission du navigateur/telephone. Apres autorisation et obtention effective d une position, transmettre use_location=true et les deux coordonnees. Si la permission est refusee, si le GPS est indisponible ou si sa lecture echoue, omettre use_location ou envoyer false, sans coordonnees : Laravel applique la ville du profil. L API ne peut pas lire elle-meme la permission ou le GPS du telephone. Les coordonnees de la requete servent au calcul et ne sont ni enregistrees en base ni renvoyees dans la reponse.

Exemples (prefixe /api/mboka-services/v1) :

GET /providers?q=electrique
GET /providers?q=electrique&use_location=true&latitude=-4.32&longitude=15.31
GET /providers?service_id=12&city_id=4&district=Gombe&min_rating=4

q recherche les noms/slugs des services ou categories (metiers), sans distinction de majuscules/minuscules. Les caracteres % et _ sont traites comme du texte, pas comme des jokers SQL. service_id et category_id permettent une selection explicite ; tous les criteres doivent correspondre a la meme offre disponible et approuvee. La liste services de chaque resultat contient uniquement les offres correspondantes. Aucun filtre de tarif n est ajoute.

Avec position, PostGIS verifie les distances en metres : les prestataires on_site doivent couvrir la position avec leur rayon configure (1-200 km), meme si leur adresse se trouve dans une autre ville. Les etablissements at_provider sont presentes jusqu a 25 km ; both peut correspondre a un deplacement chez le client et/ou a une visite en etablissement. Le rayon de recherche des etablissements est defini dans config/provider-search.php. Sans coordonnees valides du prestataire, aucune couverture GPS n est inventee. Aucun repli automatique vers une autre ville n est effectue si les resultats sont vides.

Demande, messagerie, accord et confirmation de fin

Ce parcours remplace l acceptation simple par le prestataire. Toutes les routes suivantes exigent un compte verifie et son Bearer Sanctum. Un administrateur peut consulter le dossier et traiter un probleme, mais ne confirme pas un prix ou une fin a la place du client.

Envoyer la demande

POST /service-requests conserve service_id, description (5000 caracteres maximum), provider_id et l adresse enregistree ou ponctuelle deja documentee. scheduled_date est maintenant facultatif : avant accord, il ne s agit que d une preference. Une demande sans prestataire conserve conversation_id=null ; affecter le prestataire avec PATCH /service-requests/{service_request}/assign-provider ouvre la conversation. Une demande envoyee a un prestataire ouvre sa conversation des sa creation. Les demandes de son propre profil prestataire sont refusees.

GET /service-requests/{service_request}/conversations liste les conversations du dossier (20 par page). Le client et l administrateur peuvent consulter les archives. En cas de reaffectation en discussion, une nouvelle conversation est creee et les anciennes propositions sont retirees. Le nouveau prestataire ne voit pas les anciens echanges ; l ancien prestataire perd l acces au dossier et aux fichiers de conversation. Le client conserve son historique en lecture seule. Aucune reaffectation n est possible apres accord.

Echanger des messages et des fichiers

  • GET /conversations/{conversation}/messages : historique, du plus recent au plus ancien, 30 messages par page (per_page de 1 a 100).
  • GET avec after_id=ID : messages plus recents que cet identifiant, en ordre croissant. Utile pour le rattrapage HTTP depuis React ou React Native, en complément des événements WebSocket Reverb. Les notifications push externes ne sont pas implémentées.
  • POST sur la meme route : body (5000 caracteres maximum), files[], ou les deux. Pour des fichiers utiliser multipart/form-data. Maximum 5 fichiers par message : photos 10 Mo et videos 100 Mo, formats JPEG/PNG/WebP/GIF/MP4/MOV/WebM. Au moins du texte ou un fichier est obligatoire.

Les participants recoivent des notifications en base pour les messages et etapes importantes, sans recopier le texte prive dans la notification. L historique ne se modifie pas via les routes medias.

Le Bearer doit etre envoye aussi pour charger une image ou lire une video ; le serveur accepte les lectures par plages. Les refus, annulations et interventions terminees rendent la conversation en lecture seule, mais les participants conservant l acces peuvent lire l historique.

Elles sont desormais stockees en prive et listees par GET /service-requests/{service_request}/attachments (30 par page). Les URL de fichiers exigent les memes droits que la demande. Une piece jointe ne peut pas etre deplacee vers un profil public. Les pieces jointes d un dossier restent visibles aux participants actuels ; les fichiers des messages, eux, restent isoles dans leur conversation d origine.

Convenir du prix et du rendez-vous

Les rendez-vous programmes utilisent seulement une date, sans heure. Plusieurs prestations acceptees le meme jour sont autorisees sans limite journaliere.

Le prestataire envoie POST /service-requests/{service_request}/proposals :

{"price":"25.00","currency":"USD","terms":"Diagnostic et reparation au prix convenu.","appointment_mode":"now","arrival_minutes":45}

Le prix est fixe pour cette intervention : de 0 a 9999999999.99, au maximum 2 decimales. Devises actuellement acceptees : USD et CDF. Aucun paiement ni conversion de devise n est effectue. terms decrit le travail convenu, 3000 caracteres maximum.

now signifie disponible maintenant, avec une arrivee estimee de 1 a 240 minutes apres confirmation du client. Ce n est pas une promesse d arrivee immediate. Pour un rendez-vous programme :

{"price":"25.00","currency":"USD","terms":"Diagnostic et reparation au prix convenu.","appointment_mode":"scheduled","scheduled_date":"2027-01-20"}

Utiliser une date locale YYYY-MM-DD, sans heure ni decalage UTC. Le fuseau IANA du lieu est determine par la ville et fige dans appointment_timezone lors de la proposition, puis de l accord. La date peut etre aujourd hui ; les jours passes sont refuses. Pour scheduled, arrival_minutes est ignore ; pour now, scheduled_date est ignore. Un fuseau inconnu doit etre configure sur la ville avant de proposer le rendez-vous.

Le statut passe a proposed. La proposition now expire apres 15 minutes ; une proposition scheduled apres 24 heures, ou a la fin du jour local du rendez-vous si celle-ci arrive avant. Une nouvelle proposition pendant la discussion remplace la precedente. GET /service-requests/{service_request}/proposals donne l historique de la conversation actuelle, 20 propositions par page.

Le client confirme avec PATCH /service-requests/{service_request}/proposals/{proposal}/confirm, ou refuse avec /decline. Seule une proposition encore active, de la conversation actuelle et non expiree peut etre confirmee. Le refus ramene a pending pour poursuivre la discussion. Le prix, la devise, la proposition retenue et le rendez-vous sont alors enregistres dans agreement ; accepted signifie que les deux parties sont engagees. L adresse exacte est partagee a cet accord, pas au simple envoi d une proposition.

Le montant reste fixe apres accord : aucun supplement ni modification du prix. La date peut etre changee uniquement par le parcours de report avec validation mutuelle. Un nouveau besoin exige une nouvelle demande. L ancien PATCH /service-requests/{service_request}/accept est conserve comme alias de proposition avec les memes champs obligatoires ; il ne permet plus de sauter la confirmation du client.

Realiser et terminer

  1. Le prestataire appelle PATCH /service-requests/{service_request}/start : accepted -> in_progress. Le demarrage est manuel, pas declenche automatiquement par la date du rendez-vous. Pour scheduled, il est refuse avant le debut du jour convenu dans le fuseau du lieu ; pour now, l arrivee reste une estimation et le prestataire peut demarrer en arrivant avant cette estimation.
  2. Apres le travail, il appelle PATCH /service-requests/{service_request}/complete, avec note facultative (5000 caracteres). Le statut devient awaiting_confirmation, pas completed.
  3. Le client appelle PATCH /service-requests/{service_request}/confirm-completion pour confirmer : le statut devient completed.
  4. Il peut ensuite creer son avis unique avec POST /service-requests/{service_request}/review et {"rating":5,"comment":"Travail satisfaisant"}. La note doit etre de 1 a 5 ; le commentaire est obligatoire, 3000 caracteres maximum. L avis est public sur la fiche. Le prestataire et les autres clients ne peuvent pas noter cette intervention.
  5. Les publications de realisation liees a ce dossier deviennent possibles selon le parcours de publication volontaire existant. Les fichiers de la messagerie ne deviennent jamais publics automatiquement.

Le prestataire peut refuser une demande pending ou proposed via /reject. Apres accord, il peut annuler accepted via /cancel avec reason obligatoire non vide (3000 caracteres). Le client peut annuler pending, proposed ou accepted avec reason facultatif. Auteur, role, date et motif sont conserves. Une intervention en cours ne se termine ni ne s annule par ce raccourci.

Signaler un probleme

Depuis awaiting_confirmation, le client envoie POST /service-requests/{service_request}/issues avec {"reason":"Le probleme persiste"}. Le statut devient disputed, sans ouvrir les avis et publications lies a une intervention terminee. La conversation reste ouverte pour echanger et joindre des fichiers.

GET /intervention-follow-ups est reserve aux administrateurs. PATCH /service-requests/{service_request}/issues/resolve demande action=resume_work ou cancel et resolution obligatoire (3000 caracteres). resume_work permet au prestataire de reprendre puis de declarer a nouveau la fin, au meme prix convenu. cancel ferme l intervention sans la compter comme terminee. La resolution et son auteur sont conserves. Si le probleme a ete regle entre les parties, le client peut aussi confirmer explicitement la fin depuis disputed ; cela resout le signalement et termine l intervention. Un administrateur ne force pas une bonne note ou une confirmation client.

Rappels et suivi

php artisan interventions:maintain expire les propositions, rappelle le client apres 24 heures sans confirmation et marque le dossier pour suivi administrateur apres 72 heures. Chaque rappel/escalade n est emis qu une fois par declaration de fin. Le silence ne termine pas le travail, ne genere pas d avis et ne confirme aucun prix.

La commande est planifiee toutes les heures dans le scheduler Laravel. En local, php artisan schedule:work permet de le faire tourner ; en production, configurer l execution reguliere de php artisan schedule:run. Aucun worker Horizon n est necessaire : les notifications sont conservees directement en PostgreSQL. Les durees sont definies dans config/interventions.php. Sans scheduler, le controle d expiration a la confirmation reste effectif, mais les rappels et mises a jour automatiques des statuts expires ne s executent pas.

Anciennes demandes et fichiers

La migration conserve les statuts et dates existants et cree les conversations des demandes deja affectees. Aucun prix historique n est invente. agreement.legacy=true identifie une ancienne demande sans proposition enregistree. Une ancienne intervention deja accepted ou in_progress peut continuer, mais toute nouvelle declaration de fin attend desormais la confirmation du client. Les anciens dossiers completed restent termines.

Pour les anciennes pieces jointes stockees sur le disque public, executer d abord php artisan media:privatize-interventions --dry-run, puis sans --dry-run. La commande copie, compare les empreintes et bascule le media avant de retirer la copie publique apres validation. Elle est repetable, refuse les chemins non reconnus et ne remplace pas une copie privee differente. En cas d erreur, corriger le fichier concerne et relancer ; les sources ne sont pas supprimees avant verification. Le retrait d une URL publique ne peut pas rappeler des copies deja telechargees.

La migration ne supprime aucun message ni ancienne demande. Son retour arriere est refuse si des messages, propositions, problemes, nouveaux statuts ou fichiers prives necessitent une reprise explicite des donnees.

Messagerie en temps réel : Laravel Reverb

Les messages, accords et notifications restent enregistrés dans PostgreSQL. Laravel Reverb signale les nouveaux messages (y compris les événements système : proposition, confirmation, changement de statut) et les lectures après validation de la transaction. Une annulation SQL ne diffuse aucun événement. La file de diffusion utilise la connexion redis-broadcasts et la queue broadcasts, dans Redis base 4 (REDIS_BROADCAST_DB). Redis est donc requis pour la diffusion instantanée. Les autres queues gardent leur configuration existante ; Horizon reste absent. La synchronisation multi-serveurs Reverb reste désactivée.

Démarrer en local sans Docker

Configurer REVERB_APP_ID, REVERB_APP_KEY et REVERB_APP_SECRET avec des valeurs locales aléatoires ; ne jamais transmettre le secret au frontend. Le fichier .env local a été configuré, avec BROADCAST_QUEUE_CONNECTION=redis-broadcasts et REDIS_BROADCAST_DB=4. REDIS_BROADCAST_URL permet une URL dédiée en production ; une base dans cette URL prend priorité sur REDIS_BROADCAST_DB. Utiliser BROADCAST_CONNECTION=reverb, REVERB_HOST=127.0.0.1, REVERB_PORT=18080, REVERB_SCHEME=http. REVERB_SERVER_HOST/PORT indiquent l'adresse d'écoute ; REVERB_HOST/PORT indiquent où Laravel joint le serveur. REVERB_ALLOWED_ORIGINS contient des noms d'hôtes séparés par des virgules (localhost,127.0.0.1 en local). Le serveur refuse les événements client directs : les messages doivent passer par l'API.

Dans trois terminaux, depuis le projet :

php artisan serve --host=0.0.0.0 --port=8000
php artisan reverb:start
php artisan queue:work redis-broadcasts --queue=broadcasts --tries=5 --timeout=30

Conserver aussi les processus habituels PostgreSQL/Redis pour les fonctionnalités qui en ont besoin, et le planificateur des interventions. Un arrêt de Reverb laisse les messages persistés : la file réessaie la diffusion puis place les échecs dans failed_jobs après épuisement ; utiliser php artisan queue:retry all après rétablissement, et toujours resynchroniser par HTTP. Après modification de configuration : php artisan config:clear, php artisan reverb:restart et php artisan queue:restart.

Contrat React / React Native

  1. Ouvrir une connexion compatible Pusher à Reverb, avec la clé publique REVERB_APP_KEY.
  2. Autoriser le canal via POST /api/mboka-services/v1/broadcasting/auth, JSON socket_id et channel_name=private-conversations.{id}, Authorization: Bearer <token Sanctum>, Accept: application/json. Ce token est celui de l'utilisateur connecté, pas le secret Reverb.
  3. Avec Laravel Echo, s'abonner à echo.private('conversations.' + id).listen('.conversation.updated', callback).
  4. Le payload contient conversation_id, service_request_id, type (message.created ou messages.read), message_id et reader_id (nullable). Il ne contient ni texte, ni fichier, ni adresse privée. Recharger les messages depuis GET /conversations/{id}/messages?after_id={dernier_id} et l'état de la demande depuis l'API ; pour messages.read, recharger les conversations pour leurs compteurs/accusés. Parcourir les pages de rattrapage jusqu'à épuisement, dédupliquer les messages par id.
  5. Après chaque reconnexion et chaque abonnement réussi, refaire le rattrapage HTTP. La livraison WebSocket n'est pas une garantie de réception et peut être dupliquée ou retardée.

  authorizer: channel => ({

      try {
        const response = await fetch(apiBase + '/broadcasting/auth', {
          method: 'POST',

        });
        if (!response.ok) throw new Error('Canal non autorisé');
        callback(null, await response.json());

echo.private('conversations.' + conversationId)

Sur téléphone réel, 127.0.0.1 désigne le téléphone : utiliser l'IP LAN du PC, rendre Reverb accessible sur cette interface (REVERB_SERVER_HOST), configurer les origines attendues et le pare-feu local. Ne pas exposer le secret. L'API doit aussi être joignable depuis le téléphone.

Seuls les participants autorisés et les administrateurs peuvent s'abonner à la conversation courante. Un changement de prestataire crée une autre conversation ; les anciens canaux n'acceptent plus d'abonnements et les événements encore en attente sont ignorés à l'exécution. Une socket déjà abonnée à l'ancien canal n'est pas déconnectée de force, mais aucun nouveau contenu n'y est diffusé. Les accès HTTP restent réévalués pour chaque requête, même après expiration/révocation d'un token.

En production : domaine WebSocket en WSS derrière un reverse proxy TLS, origines explicites, secrets distincts, serveur Reverb et worker supervisés, port interne non public. REVERB_SCALING_ENABLED=false pour une instance ; Redis devient nécessaire si l'on active la diffusion multi-instances. La clé publique, l'hôte et le port publics du frontend peuvent différer de l'adresse interne utilisée par Laravel.

Les événements de lecture contiennent le dernier identifiant lu ; la liste des conversations expose aussi client_read_message_id et provider_read_message_id.

Si des événements attendent déjà dans l’ancienne file PostgreSQL, la vider avec php artisan queue:work database --queue=broadcasts --stop-when-empty --tries=5 --timeout=30 pendant que Reverb fonctionne. Le changement de connexion ne déplace pas ces jobs dans Redis. Cette commande traite uniquement la file broadcasts ; conserver le worker Redis pour les nouveaux événements.

Notifications mobiles : Laravel + Expo Push

Fiabilité et reçus

Pour chaque notification enregistrée et chaque installation active, Laravel enregistre un envoi dans push_deliveries (unique par notification/installation/liaison). L'ajout dans Redis intervient après commit ; un rollback ne produit aucun envoi. L'outbox PostgreSQL permet au planificateur de reprendre après panne Redis, sans perdre l'historique. Les nouvelles notifications créées pendant EXPO_PUSH_ENABLED=false ne sont pas mises en attente rétroactivement.

Le worker réévalue session, compte vérifié, liaison actuelle, notification non lue et droits sur la prestation/conversation. Une réaffectation, une déconnexion ou un changement de token peut donc annuler un envoi obsolète. Les envois expirent après une heure. Les erreurs réseau, HTTP 429/5xx et MessageRateExceeded sont réessayées avec attente progressive, au maximum cinq tentatives. Les erreurs permanentes sont conservées sans boucle de renvoi. Les états intermédiaires d'un worker interrompu sont repris après deux minutes.

L'envoi retourne d'abord un ticket Expo, puis le planificateur vérifie le reçu à partir de quinze minutes. provider_accepted indique une remise acceptée par FCM/APNs, jamais une lecture par l'utilisateur. DeviceNotRegistered désactive uniquement la liaison concernée : un ancien reçu ne désactive pas un nouveau token. Un reçu absent après 23 heures devient unknown. Les erreurs sont journalisées par identifiant d'envoi et code, sans copier les réponses Expo ou leurs tokens.

Les envois peuvent être retardés ou dupliqués : en cas de coupure après acceptation par Expo mais avant enregistrement du ticket, il n'existe pas de garantie exactement une fois. Dédupliquer les traitements applicatifs avec notification_id ; une bannière système déjà délivrée peut toutefois être dupliquée. Les notifications en base et leur consultation HTTP restent disponibles si Expo, Redis ou le téléphone sont indisponibles. Une livraison réelle exige l'application mobile configurée et un appareil autorisé ; les tests backend utilisent des réponses Expo simulées.

Références : configuration Expo, API d'envoi, erreurs et reçus.

Alertes web : e-mail prioritaire ou Web Push après 10 minutes

Chaque nouvelle notification conserve son historique PostgreSQL et son événement Reverb. Une alerte web séparée est enregistrée dans web_notification_alerts ; aucun e-mail ni Web Push ne part avant dix minutes. Cette règle ne modifie pas les push mobiles Expo.

Tant qu'au moins un onglet web authentifié signale sa présence, même en arrière-plan, les alertes sont reportées. Après fermeture ou déconnexion, Laravel attend dix minutes sans signal web, puis vérifie à nouveau la lecture et les autorisations. Une adresse e-mail actuellement vérifiée est prioritaire ; sans adresse vérifiée, les navigateurs abonnés reçoivent Web Push. Une erreur SMTP ne provoque pas un second envoi Web Push. Sans destination disponible, seule la notification dans le compte demeure. Une lecture depuis le mobile ou le web annule l'alerte en attente.

  • PUT /notification-presence avec {"tab_id":"UUID_DE_CET_ONGLET"}, bearer Sanctum, au montage de l'application authentifiée, puis toutes les 60 secondes. Utiliser un UUID différent pour chaque document/onglet ; ne pas réutiliser un identifiant commun en localStorage. Le backend tolère 180 secondes sans signal pour la présence instantanée.

Chaque signal repousse l'alerte au minimum de dix minutes ; une fermeture explicite relance ce délai. En l'absence du signal de fermeture (crash, réseau coupé), la dernière activité connue sert de référence. Le mobile ne doit pas appeler la présence web.

Abonnement navigateur

GET /web-push/config retourne uniquement public_key, web_push_ready et delay_minutes. La clé VAPID privée n'est jamais retournée. Appeler subscribeWebPush depuis un bouton d'autorisation explicite, en HTTPS (localhost autorisé pour le développement). Déployer le Service Worker à /mboka-notifications-sw.js sur le domaine du frontend, et non celui de l'API si les domaines diffèrent. Un Service Worker existant de l'application doit intégrer ces handlers plutôt qu'être remplacé sans adaptation.

POST /web-push/subscriptions attend browser_id (UUID persistant du navigateur), browser_secret (32 octets aléatoires encodés en 64 caractères hexadécimaux minuscules), endpoint HTTPS, keys.p256dh, keys.auth et locale facultative fr/en/ln. Les champs endpoint et keys proviennent de PushSubscription.toJSON(), après pushManager.subscribe({userVisibleOnly:true, applicationServerKey:publicKey}). Le frontend génère et conserve browser_id/browser_secret localement ; leur empreinte serveur et le contenu chiffré de l'abonnement ne sont pas exposés par l'API.

Les abonnements Web Push sont conservés au logout, contrairement aux tokens Expo : ils servent précisément à alerter après déconnexion. Lors d'un changement de compte sur le même navigateur, le nouvel utilisateur se réinscrit avec la même preuve browser_secret, ce qui transfère la destination et remplace la liaison. Sans cette preuve, un conflit 409 empêche de détourner l'abonnement. Si le stockage local a été perdu mais que PushManager conserve l'ancien abonnement, se désabonner côté navigateur et créer un nouvel abonnement ; ne pas réutiliser arbitrairement un endpoint déjà lié ailleurs.

Les endpoints acceptés appartiennent aux fournisseurs connus fcm.googleapis.com, updates.push.services.mozilla.com, web.push.apple.com et aux sous-domaines de notify.windows.com. HTTP, réseaux privés, ports non standards, identifiants dans l'URL et redirections sont refusés. Les clés navigateur sont validées et les abonnements sont chiffrés dans PostgreSQL. Une réponse 404/410 désactive uniquement la liaison envoyée ; une ancienne réponse ne doit pas désactiver une liaison renouvelée. Cinq navigateurs maximum par compte.

Le Service Worker fourni affiche une notification générique, puis ouvre /notifications sur sa propre origine au clic. Les données privées sont toujours rechargées via l'API authentifiée. Le navigateur ou le système peut retarder ou bloquer les notifications ; le support Web Push varie selon le navigateur et son mode d'installation.

L'outbox est enregistrée avec la notification dans la transaction métier et reprise après panne Redis. Le worker réévalue présence, lecture, e-mail vérifié et droits sur la prestation/conversation avant l'envoi. Les erreurs temporaires sont réessayées avec attente progressive, au maximum cinq tentatives. Les confirmations d'acceptation sont conservées par liaison navigateur pour éviter de renvoyer aux navigateurs déjà servis lors d'une reprise partielle. Les envois interrompus sont repris après une lease de trois minutes ; les alertes datant de plus de sept jours sont ignorées. L'historique en base reste disponible. Aucune garantie exactement une fois n'est possible si le fournisseur accepte avant qu'une coupure empêche d'enregistrer le succès ; un e-mail ou une bannière peut exceptionnellement être dupliqué. Une alerte déjà remise au fournisseur ne peut plus être retirée après lecture ou reconnexion.

La présence et les envois sont testés avec des horloges simulées et des transports simulés. Le test Web Push chiffre réellement le payload et signe VAPID vers un handler HTTP local simulé, sans envoyer à un utilisateur. Un essai complet dans un navigateur nécessite le frontend installé, le sujet VAPID et les permissions.

Agenda personnel et rappels de rendez-vous

GET /agenda?from=2027-01-01&to=2027-01-31, Bearer Sanctum verifie. Retour data.days : chaque jour contient date et appointments (ressources de demande de prestation). Le client voit ses demandes acceptees et le prestataire ses interventions acceptees. Les prestations en cours, en attente de confirmation, en litige ou terminees restent visibles. Les demandes en discussion, refusees ou annulees sont exclues. Les comptes ayant les deux profils voient les deux ensembles. Les administrateurs ne voient que leurs propres rendez-vous.

Intervalle maximal 93 jours ; per_page 1-100 (30 par defaut). La pagination porte sur les rendez-vous, donc un jour peut continuer sur la page suivante. Chaque element porte son appointment_timezone ; le jour ne depend pas du fuseau du navigateur.

Deux rappels sont enregistres pour chaque partie : la veille a 07:30 et le jour prevu a 00:00, dans le fuseau du lieu. A Kinshasa, 07:30 correspond a 06:30 UTC ; a Lubumbashi, a 05:30 UTC. Le fuseau est conserve dans la proposition puis l accord, meme si le profil ou la ville change ensuite. Les villes de reference d Afrique centrale sont configurees ; pour une ville supplementaire, renseigner cities.timezone avec un identifiant IANA valide, surtout en RDC qui possede deux fuseaux. Aucun repli silencieux sur le fuseau du serveur.

Activer le scheduler Laravel (php artisan schedule:work en local ; schedule:run chaque minute en production). La commande php artisan appointments:remind est executee chaque minute. Un verrou SQL et des marqueurs persistants empechent les doublons lors de deux executions. Les notifications et marqueurs sont valides dans la meme transaction. Les files Reverb/Expo/web deja documentees prennent ensuite le relais ; le relais web conserve son delai de dix minutes. Les heures indiquees sont celles de creation des rappels, la livraison depend des workers et fournisseurs.

Pas de rappel anticipe pour now ni pour un horaire de rappel deja passe au moment de l accord. Les rappels cessent des que le travail commence, est annule ou termine. En cas de panne du scheduler, un rappel de la veille ne se rejoue pas le jour meme ; seul le rappel du jour peut etre rattrape pendant ce jour. Aucun rappel apres le jour prevu. Les envois externes encore en attente reverifient l accord et le statut avant de partir. L historique deja cree reste conserve. Un report accepte recalcule les rappels et invalide ceux de l ancienne version du rendez-vous.

Migration : les anciens rendez-vous dont le lieu est identifiable conservent leur jour local ; les anciennes heures sont normalisees au debut du jour. Aucun rappel deja passe n est rejoue. Les anciens lieux sans fuseau identifiable doivent etre configures avant reprise ; aucun fuseau n est invente.

Reporter un rendez-vous avec accord mutuel

Le client ou le prestataire peut proposer une autre date tant que l intervention est accepted et qu un accord de prix existe. La date et les rappels actuels restent en vigueur pendant la discussion. Un rendez-vous now peut etre deplace vers un jour programme. Les anciens dossiers sans accord de prix explicite ne sont pas convertis automatiquement.

Routes protegees par Bearer Sanctum et contact verifie :

  • POST /service-requests/{service_request}/reschedules : proposer {"scheduled_date":"2027-01-25","reason":"Autre engagement"}.
  • GET /service-requests/{service_request}/reschedules : historique de la conversation actuelle, 20 par page, plus recent d abord.
  • PATCH /service-requests/{service_request}/reschedules/{reschedule}/accept : l autre partie accepte.
  • PATCH /service-requests/{service_request}/reschedules/{reschedule}/decline : l autre partie refuse.

scheduled_date est une date YYYY-MM-DD sans heure, differente de la date actuelle, aujourd hui ou un jour a venir selon le fuseau du lieu deja conserve. reason est facultatif (1000 caracteres maximum). Le prix, la devise, le lieu, le prestataire et le fuseau ne sont pas modifiables par ce parcours. Une proposition de report n est pas un nouveau devis.

Une seule proposition peut etre en attente. Une nouvelle proposition, de l une ou l autre partie, remplace l ancienne (superseded) ; son auteur ne peut pas l accepter ou la refuser lui-meme. Il n est jamais possible d accepter un ancien report, un report d un autre dossier ou une proposition expiree. Les administrateurs peuvent lire l historique mais ne decident pas a la place des parties. Maximum 30 propositions par minute.

La proposition expire au bout de 24 heures (config/appointments.php), ou a la fin du nouveau jour local si celle-ci arrive avant. Sans accord ou en cas de refus/expiration, aucune date n est changee. La commande appointments:maintain-reschedules tourne chaque minute via le scheduler et notifie les deux parties lors de l expiration. Un demarrage ou une annulation retire immediatement les propositions en attente (withdrawn).

Une acceptation conserve le prix/devise et accepted_proposal_id, remplace seulement le jour courant et programme les rappels aux deux parties : veille 07:30 et jour 00:00, fuseau du lieu. Les horaires deja passes au moment de l acceptation ne sont pas rejoues. L agenda suit immediatement la nouvelle date. Le statut de l intervention reste accepted.

La ressource de prestation retourne appointment_revision (0 initialement, puis increment a chaque report accepte) et pending_reschedule (proposition active ou null). scheduled_date est le jour courant faisant foi. latest_proposal garde les informations du devis initial pour l historique ; sa date originale n est pas reecrite. L historique contient les statuts pending/accepted/declined/superseded/withdrawn/expired, les dates, le motif, les auteurs et les instants de reponse.

Les evenements reschedule_requested, reschedule_accepted, reschedule_declined ouvrent une notification pour l autre partie et un message systeme dans la conversation. reschedule_expired informe les deux parties. Les canaux Reverb, Expo et relais web e-mail/Web Push conservent leurs regles habituelles ; le push externe ne contient pas le motif prive. Un reschedule_id permet de retrouver la proposition via les routes protegees.

Les rappels portent maintenant appointment_revision. Un ancien rappel est ecarte avant un envoi externe si la date/version ou le statut ne correspond plus, meme lorsque la meme date a ete choisie a nouveau apres un autre report. Les notifications historiques ne sont pas effacees. Les propositions remplacees ou expirees ne declenchent plus leur ancienne alerte de demande encore en attente.

Toutes les mutations prennent le meme verrou SQL sur la prestation. Changement de date, decision, message systeme, notifications et nouveaux rappels sont enregistres dans la meme transaction. Une deuxieme acceptation ne change plus rien et retourne 422 ; les decisions sur sa propre proposition et les identifiants non autorises retournent 404.

Annulation avant demarrage par le prestataire

La route existante PATCH /service-requests/{service_request}/cancel accepte maintenant aussi le prestataire actuellement affecte, lorsque la prestation est accepted. Le corps doit contenir reason, texte non vide de 3000 caracteres maximum. Exemple : {"reason":"Indisponibilite imprevue, je ne peux pas assurer la prestation."}. Le client conserve son comportement : annulation pending/proposed/accepted avec motif facultatif.

Avant l accord, le prestataire continue a utiliser /reject pour refuser une demande pending/proposed. Apres demarrage (in_progress), en attente de confirmation, en litige ou apres completion, /cancel retourne 422 pour les deux participants. L annulation administrative depuis un litige reste disponible par /issues/resolve avec action=cancel et une resolution obligatoire ; l administrateur ne remplace pas les participants par /cancel.

La ressource de prestation contient cancellation avec by_user_id, by_role (client/provider/admin), at (instant UTC) et reason. cancellation_reason reste present pour les anciens clients API. Le champ cancellation est null si la prestation n est pas annulee. Les anciennes annulations gardent leur motif et des valeurs null pour auteur, role et instant inconnus : aucune information historique n est inventee. Les nouvelles resolutions administratives qui annulent un litige portent aussi cet audit.

L historique de conversation contient un message systeme request_cancelled avec auteur, role, instant et motif. Seul l autre participant recoit la notification d annulation ; le titre distingue client et prestataire. Le motif reste dans le dossier et la conversation prives : il n est pas ajoute au contenu externe Expo/e-mail/Web Push. L historique des notifications reste conserve.

Les dates de rappel futur sont retirees ; les envois Expo et web encore en attente reverifient le statut puis passent en skipped. Les reports pending passent en withdrawn et ne peuvent plus etre acceptes. L agenda n affiche plus la prestation annulee, les details d adresse sont de nouveau masques a l autre participant, et la conversation passe en lecture seule. Le prix convenu et la proposition de prix restent conserves pour l historique.

L operation prend le meme verrou SQL que le demarrage et les reports. Un second appel retourne 422 et ne remplace ni le motif ni l auteur du premier, ni ne cree une seconde notification. Audit, retrait des reports, message et notifications sont enregistres dans la meme transaction.

Tableau de bord du prestataire

GET /api/mboka-services/v1/provider-dashboard exige un token Sanctum, une inscription verifiee, le role prestataire et un profil prestataire actif. Un administrateur n'obtient aucune vue globale par cette route : les donnees restent celles de son propre profil prestataire.

Parametres : section (defaut requests_to_handle), page (minimum 1), per_page (15 par defaut, maximum 50). La reponse contient data.counts pour toutes les sections et data.service_requests, une liste paginee de la section choisie. meta fournit la section, l'instant de generation et la pagination ; links conserve les filtres pour les pages suivantes.

Section Contenu
requests_to_handle Demandes pending et demandes proposed sans proposition courante encore valide (notamment expiree).
awaiting_client Demandes proposed avec derniere proposition pending valide dans la conversation courante, pour ce prestataire.
accepted Prestations acceptees avant demarrage, y compris les demandes pour maintenant et les dates passees encore non demarrees.
in_progress Travaux en cours.
awaiting_confirmation Travaux declares termines, en attente de confirmation du client.
disputed Prestations avec probleme signale.
completed Travaux termines et confirmes.
upcoming Prestations acceptees et programmees aujourd'hui ou plus tard, selon le fuseau de chaque rendez-vous.

Les compteurs portent sur tout l'historique accessible du prestataire, independamment de la page. upcoming est un sous-ensemble de accepted : ne pas additionner ces deux compteurs. Les demandes annulees, refusees, supprimees ou affectees a un autre prestataire sont exclues. Les demandes avec client ou service supprime sont exclues egalement.

Les prochains rendez-vous sont tries par date locale puis identifiant, sans heure ni limite par jour. Les autres listes sont triees par derniere modification puis identifiant decroissant. Tableau de bord du client

GET /api/mboka-services/v1/client-dashboard exige un token Sanctum, une inscription verifiee, le role client et un profil client actif. Il rassemble les demandes appartenant au client connecte ; les roles prestataire ou administrateur supplementaires n'elargissent jamais cet acces.

Parametres : section (defaut awaiting_provider), page (minimum 1), per_page (15 par defaut, maximum 50). La reponse comprend data.counts pour toutes les sections, data.service_requests pour la liste paginee et meta pour la section, l'instant de generation et la pagination. Les liens first/last/prev/next conservent les filtres.

Section Contenu
awaiting_provider Demandes pending, y compris sans prestataire ; demandes proposed sans proposition courante valide ou sans prestataire actif.
proposals_to_review Dernieres propositions pending non expirees, dans la conversation courante et pour le prestataire actuellement affecte.
accepted Prestations acceptees avant demarrage.
in_progress Travaux en cours.
awaiting_confirmation Travaux declares termines par le prestataire, a confirmer par le client.
disputed Prestations avec probleme signale.
completed Prestations terminees et confirmees.
to_review Prestations completed sans avis existant, avec un prestataire actif distinct du client.
cancelled Demandes annulees.
rejected Demandes refusees.

Les propositions programmees sont aussi verifiees selon la date locale de leur rendez-vous. Une offre expiree est reclassee pour l'affichage sans modifier la base ni envoyer de notification. Les listes sont triees par derniere modification puis identifiant decroissant. Les compteurs couvrent tout l'historique, independamment de la page ; to_review est un sous-ensemble de completed, leurs compteurs ne s'additionnent pas. Les demandes ou services supprimes sont exclus. Une modification concurrente peut apparaitre au prochain rafraichissement.

links.agenda pointe vers l'agenda existant : le frontend ajoute les dates from et to pour le consulter. Aucune seconde liste de rendez-vous n'est creee dans ce tableau de bord.

Les objets respectent ServiceRequestResource et les regles d'adresse existantes : le client voit sa propre adresse ; l'adresse privee de l'etablissement du prestataire reste masquee avant accord. Reponse privee sans cache partage, limite de 60 requetes par minute.

Exemple : GET /api/mboka-services/v1/client-dashboard?section=proposals_to_review&per_page=15&page=1. Les actions (confirmer une proposition, confirmer la fin ou publier un avis) continuent d'utiliser les routes protegees existantes, qui revalident les droits et le statut au moment de l'action.
